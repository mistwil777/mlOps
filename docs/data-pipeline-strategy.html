01

Contexte et objectifs

La plateforme MLOps a pour mission de produire des adapters LoRA fine-tunés sur des modèles locaux (7B-14B 4-bit), en réponse à des besoins clients précis. L'objectif est une souveraineté totale : zéro appel cloud en production, modèles et données hébergés localement chez le client.

Le fine-tuning via LoRA nécessite des données d'entraînement de haute qualité, structurées par adapter. Ce document décrit la stratégie retenue pour collecter, qualifier, organiser et préparer ces données — depuis les sources brutes jusqu'au format exploitable par MLX-LM.

Périmètre de ce document

Ce document couvre uniquement le pipeline de données (collecte → qualification → augmentation → préparation). Il ne couvre pas l'architecture d'entraînement, d'évaluation, ni de déploiement — ceux-ci font l'objet de documents séparés.

02

Philosophie fondamentale

Qualité > Volume

Le principe central : il vaut mieux 50 données excellentes que 500 données bruyantes. Cette décision a des conséquences directes sur toute l'architecture :

✓ Décision validée — Seuil de départ

50 données excellentes par adapter comme point de départ. Ce n'est pas un volume cible fixe — c'est un seuil minimal de qualité. Le système monitore les performances post-entraînement et recommande d'ajouter des données si nécessaire, de façon ciblée.

⚠ Principe GIGO (Garbage In, Garbage Out)

Une donnée douteuse est rejetée, jamais incluse. Les données collectées ne seront pas re-collectées — la qualité est non-négociable dès le départ. Dans de nombreux projets, c'est le client qui fournit les données ; si ce n'est pas le cas, il paye les traitements computationnels.

Agnosticisme de la plateforme

La plateforme MLOps ne contient aucun code en dur lié à un domaine, un langage ou un client spécifique. Tout ce qui est spécifique à un projet est déclaré dans les fichiers YAML de configuration. Un projet "C→Rust" ou "Assistant RH" fonctionne sans toucher une seule ligne de code Python.

Règle fondamentale
  • Collecteurs : génériques, reçoivent des paramètres depuis la config
  • Verifiers : génériques, invoqués via MCP avec langage et code en paramètre
  • Scorers : méthode déclarée dans le YAML de l'adapter, pas dans le code
  • Transformations : templates YAML, pas de logique métier dans le pipeline

Rôle de l'humain

L'humain intervient le moins possible et uniquement sur le quoi, jamais sur le comment.

L'humain valide La plateforme gère
Les adapters proposés pour son besoin La configuration technique de chaque adapter
Les sources de données recommandées La collecte, le nettoyage, la déduplication
Les verifiers proposés (type de vérification souhaitée) L'installation, la configuration et l'invocation des MCP servers
La pertinence des YAMLs générés (commentés) Le scoring, la qualification, l'augmentation
Pourquoi réduire l'intervention humaine

Le savoir-faire technique fin (configuration, validation de code, vérification d'équivalence sémantique) ne peut pas être délégué à un humain non spécialiste. La plateforme et les LLMs assistent le jugement humain — ils ne le remplacent pas sur les décisions métier, mais prennent en charge toute la vérification technique.

03

Pipeline de données — ordre des étapes

Le pipeline est strictement séquentiel. Chaque étape est un filtre : seules les données qui passent progressent vers l'étape suivante. Les rejets sont loggés avec leur motif.

Étape 1
Collecte brute
Sources déclarées par adapter dans le YAML projet. Collecteurs génériques (multilang_wiki, doc_crawl, web_crawl, manual). Output : enregistrements bruts avec métadonnées (source, date, langue, contexte).
Coût : ~0 (scraping) — variable selon volume
↓
Étape 2
Vérification structurelle (software)
Via MCP servers. Syntaxe valide ? Longueur minimale ? Langue correctement détectée ? Code exécutable ? Filtres déterministes, rapides, coût nul. Rejette ~20-30% des records bruts.
Coût : 0 — déterministe et local
↓
Étape 3
Scoring de pertinence (LLM)
Méthode déclarée dans le YAML de l'adapter (cosine+euclidean pour le juridique, TDV+cosine pour le code). Haiku par défaut, routé vers Sonnet pour les cas complexes. Score de pertinence par rapport à la tâche de l'adapter.
Coût : ~0.50€/adapter (Haiku) — principal levier de réduction
↓
Étape 4
Vérification sémantique (software + LLM)
Pour le code : exécution sandboxée via MCP, comparaison d'outputs. Le LLM n'intervient que sur ce que le software ne peut pas trancher. Pour le texte : LLM juge (Sonnet) sur un sous-ensemble filtré par l'étape 3.
Coût : ~5-15€/adapter (Sonnet sur volume réduit)
↓
Étape 5
Déduplication
Hash sur contenu normalisé. Détection des doublons sémantiques proches via embedding. Suppression des variantes trop similaires qui n'apportent pas de diversité.
Coût : ~0 (déterministe) + embedding si similarité sémantique
↓
Étape 6
Couverture des catégories
Clustering des données validées. Comparaison avec les catégories attendues définies par l'advisor. Identification des gaps → recommandations ciblées de collecte supplémentaire.
Coût : ~0.20€ (embedding + clustering local)
↓
Étape 7
Augmentation (optionnelle)
Uniquement sur les données ayant passé TOUTES les étapes précédentes. Inspirée de la data augmentation en Computer Vision : transformations qui préservent la relation sémantique. Vérifiée par exécution.
Coût : ~3-10€/adapter (Sonnet pour génération + vérification)
↓
Étape 8
Transformation → format entraînable
Transformation en paires {prompt, completion} via templates YAML (config/transforms/). C'est LA SEULE étape où le format d'entraînement est appliqué. Formatage final pour MLX-LM LoRA.
Coût : ~0.20€ (Haiku pour formatage)
⚠ Point critique — Ordre inviolable

La transformation en paires {prompt, completion} se fait uniquement à l'étape 8. Les étapes 1 à 7 opèrent sur les données dans leur schéma natif (description/code, task_name/code, etc.). Appliquer le format d'entraînement plus tôt pollue la qualification et masque les problèmes de qualité.

04

Mesure de la valeur d'une donnée

La méthode de scoring est déclarée dans le YAML de l'adapter selon son domaine. Pas de méthode universelle codée en dur. L'advisor recommande la méthode de scoring en même temps qu'il recommande l'adapter.

# Exemple YAML adapter — domaine juridique scoring: method: cosine_euclidean # similarité cosinus + distance euclidienne threshold: 0.82 # score minimum pour passer l'étape reference_examples: 5 # exemples "idéaux" définis lors de l'analyse du besoin # Exemple YAML adapter — migration de code scoring: method: tdv_cosine # test-driven validation + cosinus threshold: pass_rate: 0.95 # 95% des tests unitaires doivent passer semantic_score: 0.78 # score sémantique minimum
Méthode Domaine adapté Coût Fiabilité
cosine + euclidean Juridique, RH, texte structuré Très faible (embedding local) Bonne sur contenu homogène
TDV (test-driven) Code — migration, génération Faible (exécution locale) Excellente — vérification déterministe
LLM juge (Sonnet) Cas complexes, ambigu, métier Moyen (~0.02€/record) Bonne mais coûteuse — réserver aux cas difficiles
Heuristiques Premier filtre universel Nul Faible sur le fond — indispensable en pré-filtre
05

Stockage des données par adapter

✓ Décision validée — Isolation par adapter

Chaque adapter dispose de ses propres données isolées dans le datalake. La duplication d'une donnée utile à deux adapters est acceptée.

datalake/projects/{project_id}/ adapters/ {adapter_name}/ raw/ # données brutes collectées validated/ # données ayant passé les filtres augmented/ # données augmentées (si applicable) ready/ # format final {prompt, completion}
Avantages de l'isolation par adapter Inconvénients acceptés
Pipeline indépendant par adapter — un adapter peut être recollecté sans impacter les autres Duplication si une donnée sert plusieurs adapters
Suppression propre — supprimer un adapter supprime toutes ses données Stockage légèrement plus important
Audit clair — traçabilité complète par adapter —
Pas de couplage — modifier les données d'un adapter n'impacte pas les autres
06

Augmentation des données

Inspirée de la data augmentation en Computer Vision : en CV, une rotation d'image préserve le label (un chat reste un chat). En MLOps, la règle équivalente est que toute transformation doit préserver la relation sémantique entre les données.

⚠ Condition préalable stricte

L'augmentation ne s'applique que sur des données ayant passé TOUS les filtres de qualité. Jamais sur de la data brute ou partiellement validée. Augmenter de la mauvaise data ne fait qu'amplifier le bruit.

Transformations valides

Ce qui préserve la relation sémantique
  • Renommage de variables — x, y, z → noms sémantiques (count, index, result)
  • Variations de style — même algorithme en impératif vs fonctionnel
  • Montée en complexité contrôlée — ajouter gestion d'erreurs, cas limites, types
  • Équivalents algorithmiques — bubble sort ↔ insertion sort (même complexité cognitive)

Transformations invalides (GIGO)

Ce qui introduit du bruit
  • Traduction automatique des commentaires sans compréhension du code
  • Substitution de tokens aléatoire — équivalent du bruit gaussien en CV
  • Code non vérifiable — toute augmentation doit être vérifiée par exécution
  • Généralisation excessive — créer des cas qui n'existent pas dans la vraie base client
✓ Règle de vérification — Exécution obligatoire

Pour le code : outputs identiques sur un ensemble d'inputs de test = augmentation valide. Pour le texte : LLM juge vérifie la cohérence sémantique. Augmenter peu mais rigoureusement — pas d'augmentation massive avec vérification par échantillon.

07

Recommandation ciblée d'ajout de données

Le système surveille les performances post-entraînement et recommande d'ajouter des données si nécessaire. La recommandation est ciblée par catégorie de faiblesse — pas générique.

✓ Option retenue — Advisor + Clustering

L'advisor définit à l'analyse du besoin les catégories de tâches attendues pour l'adapter. Après collecte et validation, un clustering vérifie quelles catégories sont effectivement couvertes. Les gaps = recommandations ciblées.

# Exemple de recommandation générée automatiquement { "adapter": "syntax_translator", "evaluation_score": 0.71, # sous le seuil 0.85 "weak_categories": [ { "category": "gestion_exceptions", "coverage": 0.23, # sous-représenté "recommended_additions": 18, "suggested_sources": ["docs.oracle.com/exceptions"] } ] }

Déclencheurs de recommandation

Signal Interprétation Action recommandée
Score global < quality_thresholds Performance insuffisante Analyser les catégories faibles, cibler la collecte
Catégorie < 20% de couverture Angle mort dans les données Collecte ciblée sur cette catégorie spécifique
Loss non saturée en fin d'entraînement Modèle n'a pas convergé — volume insuffisant Ajouter des données sur les catégories principales
08

Verifiers — outils de vérification via MCP

Les verifiers sont des outils de vérification invoqués via MCP servers. Ils sont recommandés par l'advisor (Sonnet) à l'analyse du besoin, déclarés dans le YAML projet avec commentaires, validés par l'humain, puis gérés entièrement automatiquement.

✓ Architecture retenue

Un registre config/verifiers/registry.yaml liste les MCP servers disponibles. L'advisor consulte ce registre et recommande les verifiers selon la tâche de chaque adapter. Les YAMLs générés sont commentés et proposés avant persistance. Après validation humaine : 100% automatique.

# Exemple section verifiers dans un YAML projet verifiers: # Vérifie que le code Python est syntaxiquement valide et s'exécute # Filtre ~30% des records bruts — coût nul - id: python_exec type: mcp_tool server: code-executor validates: [syntax_translator] # Vérifie l'équivalence outputs Python/Java sur inputs de test # Remplace un LLM juge pour les cas déterministes — coût nul - id: semantic_diff type: mcp_tool server: code-executor validates: [syntax_translator]
Critère MCP vs LLM

Un MCP server a du sens quand la tâche est déterministe + rapide + appelée très souvent. Sinon, un LLM est plus flexible. Les MCP servers créés pour mlOps seront génériques : "code-executor" reçoit un langage et du code en paramètre — jamais un "python-executor" dédié.

09

Coûts computationnels et LLM

Les coûts LLM sont le poste dominant, devant le compute. La stratégie "peu de données très qualitatives" réduit les coûts en limitant le volume à scorer et vérifier.

Poste Par adapter Projet 5 adapters Levier de réduction
Collecte / scraping 1 à 3€ 5 à 15€ Sources ciblées, volume limité
Scoring qualité (Haiku) ~0.50€ ~2.50€ Pré-filtres déterministes en amont
Vérification sémantique (Sonnet) 5 à 15€ 25 à 75€ Software (MCP) traite les cas déterministes
Augmentation (Sonnet) 3 à 10€ 15 à 50€ Uniquement sur data déjà validée
Entraînement LoRA (A10G cloud) 8 à 20€ 40 à 100€ Local sur M4 Pro = quasi gratuit
Évaluation vs baseline 2 à 8€ 10 à 40€ —
Coût total estimé — projet 5 adapters (client sans data)
100 à 280 €
Réduction long terme — Nos propres adapters comme agents

Une fois entraînés, nos adapters de scoring et de vérification tournent en local via Ollama à coût nul. La plateforme devient progressivement son propre client — chaque projet améliore les outils qui servent aux projets suivants.

10

Agents et outils à construire

Liste des agents et outils nécessaires au pipeline de données. Aucun n'est encore construit — ce document sert de feuille de route. Ils doivent tous être construits avant d'être utilisés.

Agents LLM

data-scorer
Score la pertinence de chaque enregistrement brut par rapport à la tâche d'un adapter. Route vers Haiku (cas simples) ou Sonnet (cas complexes) selon la difficulté détectée.
Modèle : Haiku 4.5 (défaut) / Sonnet 4.6 (complexe)
Input : record brut + description tâche adapter + méthode scoring
Output : score 0-1 + motif + catégorie détectée
Étape pipeline : 3 — Scoring de pertinence
semantic-judge
Vérifie l'équivalence sémantique entre deux implémentations (code ou texte) quand le software ne peut pas trancher. Juge si la relation entre les deux éléments est préservée.
Modèle : Sonnet 4.6
Input : deux implémentations + contexte de la tâche
Output : équivalent/non-équivalent + explication
Étape pipeline : 4 — Vérification sémantique
data-augmentor
Génère des variantes d'augmentation à partir de données validées. Applique les transformations autorisées (renommage, style, complexité) en préservant la relation sémantique.
Modèle : Sonnet 4.6
Input : donnée validée + type de transformation + contraintes adapter
Output : N variantes + métadonnées de transformation
Étape pipeline : 7 — Augmentation
coverage-analyst
Compare les catégories de tâches attendues (définies par l'advisor) avec les catégories effectivement couvertes par les données validées. Génère les recommandations ciblées d'ajout.
Modèle : Haiku 4.5 + clustering local
Input : données validées + catégories attendues YAML
Output : rapport de couverture + recommandations ciblées
Étape pipeline : 6 — Couverture des catégories
data-transformer
Transforme les données validées en paires {prompt, completion} selon le template déclaré dans le YAML de l'adapter. C'est la seule étape où le format d'entraînement est appliqué.
Modèle : Haiku 4.5
Input : données validées + template config/transforms/
Output : paires {prompt, completion} formatées pour MLX-LM
Étape pipeline : 8 — Transformation
verifier-recommender
Recommande les verifiers MCP appropriés lors de l'analyse du besoin. Consulte le registre config/verifiers/registry.yaml et sélectionne selon le domaine et les tâches de chaque adapter.
Modèle : Sonnet 4.6 (intégré à l'advisor)
Input : description adapter + registre verifiers disponibles
Output : section verifiers du YAML projet, commentée
Étape pipeline : Analyse du besoin (pré-collecte)

Outils MCP à créer

mcp/code-executor
Exécution sandboxée de code dans n'importe quel langage. Reçoit langage + code + inputs de test, retourne outputs et erreurs. Générique — jamais spécifique à un langage.
Tools exposés : execute(lang, code, inputs), lint(lang, code)
Backend : Python natif + Docker pour les autres langages
Utilisé par : semantic-judge, data-augmentor (vérification)
mcp/data-quality
Outils déterministes de qualification des données brutes : détection de langue, validation de structure JSONL, détection de doublons, scoring de longueur et de densité.
Tools exposés : detect_lang(text), dedup(records), validate_schema(record), length_score(text)
Coût : 0 — entièrement local et déterministe
Utilisé par : Étape 2 (filtrage structurel)

Outils pipeline (scripts Python)

pipeline/cluster.py
Clustering des données validées par adapter. Utilise les embeddings nomic-embed-text (Ollama local). Produit les clusters et les compare aux catégories attendues du YAML adapter.
Input : datalake/.../validated/ + YAML adapter (catégories attendues)
Output : rapport de couverture JSON + gaps identifiés
pipeline/deduplicate.py
Déduplication à deux niveaux : hash exact sur contenu normalisé, puis similarité sémantique via embedding pour détecter les quasi-doublons.
Input : datalake/.../raw/consolidated.jsonl
Output : fichier dédupliqué + rapport des rejets
pipeline/transform.py
Transformation des données validées en paires {prompt, completion} selon le template déclaré dans config/transforms/. Seule étape où le format d'entraînement est appliqué.
Input : datalake/.../validated/ + config/transforms/{template}.yaml
Output : datalake/.../ready/pairs.jsonl
pipeline/recommend.py
Analyse les métriques post-entraînement MLflow et les gaps de couverture pour produire des recommandations ciblées d'ajout de données par catégorie de faiblesse.
Input : MLflow run_id + rapport couverture cluster.py
Output : recommandations JSON + sources suggérées
11

Ordre de construction recommandé

Construire tous les outils avant de les utiliser. Cet ordre respecte les dépendances : chaque outil s'appuie sur les précédents.

1
config/verifiers/registry.yaml Config
Registre des MCP servers disponibles — le référentiel que tous les autres composants consultent. Définit le contrat d'interface.
2
mcp/data-quality MCP
Outils déterministes sans dépendances. Actif dès l'étape 2 du pipeline. Coût nul — à construire en priorité pour réduire le volume traité par les LLMs en aval.
3
mcp/code-executor MCP
Exécution sandboxée générique. Prérequis pour le TDV (scoring code) et pour la vérification des augmentations. Python natif d'abord, Docker pour les autres langages.
4
pipeline/deduplicate.py Script
Dépend uniquement du datalake. Doit tourner avant tout scoring LLM pour ne pas payer pour scorer des doublons.
5
agents/data-scorer Agent LLM
Dépend de mcp/data-quality (pré-filtre) et du registre verifiers. Premier agent LLM du pipeline — son routing Haiku/Sonnet doit être calibré sur des exemples réels.
6
agents/semantic-judge Agent LLM
Dépend de mcp/code-executor. N'intervient qu'après que le software a traité les cas déterministes.
7
pipeline/cluster.py Script
Dépend des données validées (étapes 2-4) et des embeddings Ollama. Prérequis pour coverage-analyst et recommend.py.
8
pipeline/transform.py Script
Transformation finale en paires d'entraînement. Dépend des templates config/transforms/ (déjà partiellement existants).
9
agents/data-augmentor Agent LLM
Dépend de mcp/code-executor (vérification) et de données déjà validées. Construit en dernier car optionnel — le pipeline fonctionne sans lui.
10
pipeline/recommend.py + agents/coverage-analyst Script Agent LLM
Dépend de MLflow (métriques entraînement) et de cluster.py. Construit après le premier cycle entraînement complet — nécessite des données réelles d'évaluation pour être calibré.
✓ Principe — Construire avant d'utiliser

Aucun outil ne doit être invoqué dans un pipeline réel avant d'avoir été testé en isolation. L'ordre ci-dessus garantit que chaque outil est disponible et validé quand le suivant en a besoin.
