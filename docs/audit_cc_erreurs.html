Audit CC — Erreurs et corrections

Rapport post-audit : travail de Claude Code (session novembre 2026) revu et corrigé par Wilfried Leroulier

Branche auditée : chore/domain-agnostic Commits de correction : a796fac, 548fa6a, 71b1c0f, 3a22621 Source : messages de commits + fichiers source uniquement

L'audit réalisé sur PC personnel a identifié quatre catégories d'erreurs : (1) suppressions abusives de fichiers génériques confondus à tort avec du code Migrator, (2) hardcoding domaine non retiré du code exécutable, (3) état des jobs maintenu en mémoire vive (perte au redémarrage), (4) appels LLM directs hors gateway — sans contrôle de classification ni audit. Ces erreurs ont conduit à la création de 4 commits de correction, 3 nouveaux tests-gardes, 1 hook Stop automatique, et 4 nouvelles règles CLAUDE.md.

Note de cadrage : la suppression de pipeline/checks/syntax.py, des 4 fixers, et des configs code (languages.yaml, code.yaml, code_migration.yaml, doc_to_code.yaml) était intentionnelle et correcte — MLOps ne cible pas le code (les SLMs spécialisés existants couvrent ce besoin). Ces suppressions ne sont pas des erreurs.

1. Erreurs commises par CC

A — Suppressions abusives

Suppression de agents/pair_fuser.py, agents/semantic_pair_matcher.py
agents/pair_fuser.py · agents/semantic_pair_matcher.py
Motif invoqué : "supprimer toute trace Migrator". Erreur : ces fichiers ne sont pas spécifiques à Migrator — pair_fuser est utilisable pour tout projet multilingue, semantic_pair_matcher pour tout matching sémantique. La plateforme doit rester agnostique par configuration, pas par suppression de fonctionnalités génériques. Les deux fichiers ont été réintroduits dans a796fac.
Suppression de pipeline/generate_bilingual.py et pipeline/tune_pipeline.py
pipeline/generate_bilingual.py · pipeline/tune_pipeline.py
Erreur : fichiers de pipeline applicables à des projets multilingues (HR, défense, documentation). Suppression sans vérification d'usage. Réintroduits dans a796fac.
Suppression partielle des web collectors (seulement une partie retirée)
agents/doc_collector.py · agents/source_discoverer.py · agents/synthetic_collector.py · agents/web_collector.py · config/trusted_domains.yaml
Le commit 548fa6a note explicitement : "was only half-removed by cdf9627". CC avait supprimé certains collectors mais pas d'autres de façon incohérente, laissant le repo dans un état intermédiaire incohérent. L'utilisateur a finalisé la suppression proprement (ces collectors étant réellement hors scope de la plateforme).

Makefile

C — Architecture état des jobs : dict mémoire vive

_JOBS dict en mémoire dans api/routers/data.py — perte d'état au redémarrage
api/routers/data.py · api/routers/rag.py · api/routers/kpis.py
CC utilisait un dict Python _JOBS en mémoire pour stocker l'état et les logs des jobs. Problèmes : (1) toute relance du serveur API efface tous les jobs en cours — l'UI affiche "not found" ; (2) les workers Celery ne peuvent pas écrire dans ce dict (processus différents) ; (3) aucune persistance. L'utilisateur a remplacé par un ledger SQLite durable (pipeline/utils/run_ledger.py) et un client HTTP (pipeline/utils/ledger_client.py) pour que les workers Celery reportent via l'API sans accès direct au fichier SQLite. Corrigé dans a796fac.
_run_clean_raw / _run_generate_pairs asyncio — code mort non supprimé
api/routers/data.py
CC avait laissé dans data.py des fonctions asyncio (_run_clean_raw, _run_generate_pairs) jamais appelées depuis la migration vers Celery. Ces fonctions créaient de la confusion sur le chemin réel d'exécution. Supprimées dans a796fac.

D — Appels LLM directs hors gateway

Appels boto3/anthropic directs dans le code sans contrôle de classification ni audit
agents/pair_generator.py · agents/pair_fuser.py · agents/semantic_judge.py · pipeline/utils/llm.py · api/routers/data.py
Plusieurs fichiers appelaient directement boto3 (Bedrock) ou le SDK Anthropic sans passer par un gateway centralisé. Pour un projet Défense classifié secret, cela signifiait que des données pouvaient être envoyées vers le cloud sans contrôle. L'utilisateur a créé pipeline/utils/llm.py comme gateway unique avec politique par classification (config/llm_policy.yaml : interne → cloud, confidentiel → cloud anonymisé, secret → local only), audit écrit avant l'envoi, et anonymisation réversible (pipeline/utils/anonymizer.py). Corrigé dans 3a22621.

3. Nouvelles règles CLAUDE.md (règles 11–14)

Règle 11
Zero hardcoded domain
Interdit tout nom de projet, langage, métrique ou persona dans le code exécutable. Domaines, langues et métriques sont des données de configuration (config/, evals/domains/), jamais des constantes dans pipeline/, agents/ ou api/.
Enforcement : tests/test_no_domain_hardcoding.py — ratchet sur tests/domain_hardcoding_baseline.json (ne peut que diminuer, jamais augmenter). Exécuté automatiquement par le hook Stop.
Règle 12
Job state dans le ledger durable — pas en mémoire
Interdit les dicts _JOBS ou tout autre état de job in-process dans api/. L'état vit dans le ledger SQLite (pipeline/utils/run_ledger.py). Les workers Celery ne peuvent pas ouvrir le fichier SQLite directement : ils passent par POST /api/jobs/{id}/report. data.py _enqueue garantit que job_id == task_id.
Enforcement : tests/test_no_in_memory_job_state.py + hook Stop.
Règle 13
Tout appel LLM textuel passe par pipeline/utils/llm.py avec project_id
Interdit les appels directs à boto3, anthropic SDK ou tout autre provider LLM en dehors du gateway. Le gateway applique la politique de classification du projet (config/llm_policy.yaml) et écrit l'audit avant d'envoyer. Non couvert encore : embeddings, vision/OCR, l'advisor, documents CDC uploadés.
Enforcement : tests/test_no_direct_llm_calls.py (ratchet, baseline ne peut que diminuer) + hook Stop.
Règle 14
Une tâche est terminée uniquement avec preuve concrète
Interdit les affirmations du type "ça devrait fonctionner". Une tâche est déclarée terminée uniquement si accompagnée d'une preuve : sortie de commande, logs, capture d'écran. Si une instruction n'a été qu'en partie appliquée, le dire explicitement.
Pas de test automatique — règle comportementale pour CC.

4. Nouvelles gardes architecturales

tests/test_no_domain_hardcoding.py — ratchet hardcoding
Scanne les fichiers sources à la recherche de termes de domaine hardcodés (noms de projets, langages spécifiques, métriques de domaine). Compare le compte d'occurrences à la baseline domain_hardcoding_baseline.json. Si un fichier augmente ses occurrences ou qu'un nouveau fichier apparaît dans la baseline, le test échoue. La baseline ne peut être réduite que via python tests/test_no_domain_hardcoding.py --shrink.
tests/test_no_in_memory_job_state.py — interdit dict _JOBS
Vérifie qu'aucun fichier dans api/ ne contient de dict de job en mémoire (pattern _JOBS ou équivalent). Échoue immédiatement si une réintroduction est détectée.
tests/test_no_direct_llm_calls.py — ratchet appels LLM directs
Détecte les appels directs à des providers LLM hors pipeline/utils/llm.py et les appels sans project_id=. Ratchet : la baseline ne peut que diminuer.
scripts/hooks/guard_stop.py — hook Stop automatique
S'exécute à chaque fin de tour Claude Code (hook Stop dans .claude/settings.json). Charge et exécute les trois tests-gardes ci-dessus avec stdlib uniquement (pas de pytest, fonctionne hors venv). Retourne exit 2 si une garde échoue, ce qui renvoie le message d'erreur à CC pour correction immédiate. stop_hook_active évite les boucles infinies.
