1. Vue d'ensemble

En résumé

Entraîner un modèle d'IA sur de mauvaises données produit un mauvais modèle — c'est ce qu'on appelle le principe GIGO (Garbage In, Garbage Out). Ce pipeline est notre système de filtrage : il prend des dizaines de milliers de données brutes collectées sur le web, les analyse, les nettoie, les organise et ne conserve que ce qui est réellement utile pour l'entraînement. Le processus est entièrement automatique, reproductible, et chaque décision de filtrage est tracée.

Le pipeline transforme des données brutes collectées depuis des sources hétérogènes (documentation officielle, Rosetta Code, GitHub, saisie manuelle) en paires d'entraînement prompt/completion de haute qualité, prêtes pour le fine-tuning local.

Position dans la chaîne MLOps complète

Collecte  →  [Étape 1: clean_raw]  →  [Étapes 2/2bis: formation paires]  →  [Étape 3: clean]  →  Entraînement (mlx_lm.lora)

Ce document couvre les trois étapes de nettoyage. La collecte (en amont) et l'entraînement (en aval) sont documentés séparément.

2. Architecture agnostique — Config-driven

En résumé

Le pipeline ne contient aucune logique spécifique à un projet, une langue ou un domaine. Tout le comportement est piloté par deux champs dans config/projects/<id>.yaml : domain (qui scorer heuristique utiliser) et task_type (quelle stratégie de paires et quel template appliquer). Les collecteurs, scorers et transformateurs n'ont pas connaissance du projet dans lequel ils opèrent.

Le champ domain dans la config projet sélectionne automatiquement le scorer heuristique approprié (_code_score vs _text_score) et les techniques d'augmentation compatibles.

3. Le moteur de comparaison — Embeddings

En résumé

Pour détecter si deux textes parlent du même sujet (même si les mots sont différents), le pipeline utilise des embeddings : chaque texte est converti en un vecteur numérique, et la proximité entre deux vecteurs indique leur ressemblance sémantique. Ce mécanisme est utilisé dans trois étapes du pipeline. Plusieurs moteurs sont disponibles en cascade : si l'un est indisponible, le suivant prend le relais automatiquement.

1
AWS Bedrock — Titan Embed Text v2 Prioritaire
Modèle amazon.titan-embed-text-v2:0 · Vecteurs de dimension 1024 · Passe le filtre ZScaler Capgemini · 20 appels en parallèle · Recommandé sur réseau entreprise
2
Ollama — nomic-embed-text
Serveur local localhost:11434 · Vecteurs 768 dimensions · Bloqué par ZScaler sur réseau Capgemini · Disponible hors réseau ou VPN split-tunnel
3
sentence-transformers — nomic-embed-text v1.5
Exécuté en local via Python · Vecteurs 768 dimensions · Nécessite pip install sentence-transformers · Bon de secours si Bedrock et Ollama sont inaccessibles
4
TF-IDF (scikit-learn) Dernier recours
Toujours disponible, sans installation supplémentaire · Qualité dégradée pour les comparaisons inter-langues · Le scoring de pertinence par adapter est désactivé automatiquement dans ce mode
⚠
Mode TF-IDF et pertinence : le TF-IDF crée un vocabulaire spécifique à chaque corpus. Comparer un texte hors-corpus (la description d'un adapter) avec les records collectés produit des scores proches de zéro même pour des données pertinentes. Le pipeline le détecte et neutralise le filtre de pertinence (score fixé à 0.50 pour tous), plutôt que de rejeter des données valides par erreur.

4. Étape 1 — Nettoyage des données brutes (clean_raw.py)

En résumé

C'est l'étape la plus importante du pipeline. Elle prend les données collectées sur le web (20 000+ records bruts) et les passe à travers 7 filtres successifs. À la fin, chaque adapter ne conserve que ses données les plus pertinentes, sans doublons, dans le bon volume cible. Sur un projet type, environ 75% des données brutes sont filtrées — ce qui est normal et voulu : mieux vaut 1 000 données excellentes que 10 000 données de qualité inégale.

Entrée datalake/projects/<projet>/raw/*.jsonl — Immutable après ingestion

Sortie datalake/projects/<projet>/processed/clean_raw/<adapter>.jsonl — Un fichier par adapter

1

Déduplication exacte

Un empreinte numérique (hash MD5) est calculée pour chaque record. Si deux records ont exactement le même contenu, le second est supprimé. Simple, rapide, sans faux positifs.

Avant — 2 records identiques
{ "task_name": "fibonacci",
  "lang": "Python",
  "code": "def fib(n): ..." }

{ "task_name": "fibonacci",  ← doublon
  "lang": "Python",
  "code": "def fib(n): ..." }
Après — 1 seul record
{ "task_name": "fibonacci",
  "lang": "Python",
  "code": "def fib(n): ..." }

← supprimé (doublon exact)
Ce qui change : le second record identique est supprimé — seule la première occurrence est conservée.
Pourquoi : deux fois le même exemple n'apprend rien de plus au modèle ; cela gaspille de la capacité d'entraînement.
Ce que ça apporte : évite que le modèle sur-apprenne un pattern spécifique au détriment de la généralisation.
9 051→6 459
Exemple adapter java-to-python-translator — 2 592 doublons exacts supprimés
~29% de doublons — fréquent quand plusieurs sources couvrent les mêmes algorithmes
2

Scoring heuristique — Qualité structurelle

Chaque record reçoit un score de 0 à 1 basé sur des critères objectifs adaptés au domaine. Le scorer est sélectionné automatiquement d'après le champ domain de la config projet. Les records sous le seuil 0,55 sont définitivement rejetés.

Critères — domaine code

CritèreImpact

Mot-clé code présent (def, class, public, void, if, for…)+0.20
Description > 20 caractères+0.15
3 lignes de code minimum (\n count ≥ 3)+0.10
Lang=python : syntaxe valide via ast.parse()+0.15
Lang=java : ≥2 mots-clés Java structurels (public, class, void…)+0.15
Lang=java : accolades équilibrées ({=})+0.05
Lang=python : syntaxe invalide−0.10
Ressemble à un titre de page (regex 1ère ligne)−0.15

Critères — domaine text

CritèreImpact
Longueur 100–4000 caractères+0.40
Entropie linguistique élevée (>4.0)+0.25
Entropie moyenne (3.0–4.0)+0.10

Exemple avant/après — domaine text (FAQ juridique)

Conservé : longueur OK (+0.40), entropie 4.2 (+0.25), 3 phrases (+0.10) → score 0,75 ≥ 0,55

ℹ

3

Déduplication sémantique

Deux records peuvent parler de la même chose avec des mots différents. La déduplication exacte ne les repère pas. Ici, on compare les vecteurs d'embedding : si deux records ont une similarité cosinus ≥ 0,92, l'un est supprimé. Les vecteurs calculés ici sont réutilisés aux étapes suivantes pour éviter de rappeler Bedrock.

Avant — quasi-doublons
"Write a Python function for Fibonacci"
code: def fib(n): ...

"Implement the Fibonacci sequence in Python"
code: def fib(n): ...
→ cosinus = 0.96 ≥ 0.92
Après
"Write a Python function for Fibonacci"
code: def fib(n): ...

← supprimé (near-duplicate, cosinus 0.96)
Ce qui change : la deuxième description ("Implement…") est supprimée même si les mots sont différents — le code produit est identique.
Pourquoi : deux descriptions quasi-identiques sur le même code constituent un doublon sémantique, invisible à la déduplication exacte.
Ce que ça apporte : diversité réelle du dataset, sans sur-représentation cachée d'un même concept sous des formulations légèrement différentes.
4

Scoring de pertinence

Chaque record est comparé à la description textuelle de son adapter cible. Un record hors-sujet est identifié et réassigné ou supprimé. Le seuil est volontairement bas (0,05) car la comparaison code/prose ou question/description produit naturellement des scores faibles même pour des données pertinentes.

Exemple — adapter junit-to-pytest
Description adapter :
"Convertit les tests JUnit en tests pytest..."

Record A : "JUnit 5 @Test annotation example"
→ cosinus = 0.23 ✓ conservé

Record B : "Spring Boot DataSource config"
→ cosinus = 0.02 ✗ rejeté (hors-sujet)
Score composite
score_final =
  0.6 × score_heuristique
+ 0.4 × score_pertinence

Ce score composite détermine
quels records garder quand
le volume dépasse la cible.
5

Contrôle de volume

Chaque adapter a un volume cible défini dans sa configuration. Si on a trop de données, les moins bonnes sont éliminées. Si on en a trop peu, des variantes synthétiques sont générées automatiquement — toujours vérifiées (syntaxiquement pour le code, par longueur pour le texte).

SituationDéclencheurAction
Volume suffisantEntre 50% et 110% de la cibleAucune action
Volume excessifPlus de 110% de la cibleOn garde les meilleurs, le reste est supprimé
Volume insuffisantMoins de 50% de la cibleAugmentation synthétique déclenchée

Techniques d'augmentation disponibles

TechniqueDomaineCe que ça faitVérification

loop_stylecodeConvertit un for en while équivalent (Python uniquement)Vérification syntaxique AST obligatoire

6

Analyse de couverture thématique

Un algorithme de clustering (K-means, 8 groupes par défaut) regroupe les records par thème. Si certains groupes sont sous-représentés (moins de 40% de la taille moyenne), ils sont signalés comme "gaps". Ces gaps guident l'augmentation synthétique : les records des clusters manquants sont priorisés pour générer des variantes, garantissant que le modèle verra une diversité thématique équilibrée.

Exemple — adapter java-to-python
Cluster 0 : Algorithmes de tri     → 120
Cluster 1 : Structures de données  → 95
Cluster 2 : OOP / classes          → 88
Cluster 3 : Lambdas / streams      →  18  ← GAP
Cluster 4 : Generics Java          →  12  ← GAP
Action
Les records des clusters 3 et 4
sont priorisés lors de l'étape
d'augmentation, pour rééquilibrer
la distribution thématique avant
le fine-tuning.
7

Réassignation cross-adapter

Exécuté en amont sur l'ensemble des adapters. Si un record collecté dans l'adapter A est sémantiquement plus proche de l'adapter B (avec une marge de +15 points de cosinus), il est automatiquement déplacé vers B. Cela corrige les erreurs d'attribution lors de la collecte.

Exemple de réassignation
Record : "Spring @Entity annotation"
Présent dans : java-to-python-translator

Similarité avec java-to-python     = 0.31
Similarité avec jpa-hibernate      = 0.67
→ Marge = 0.36 > 0.15
Résultat
Record déplacé vers :
jpa-hibernate-to-sqlalchemy-migrator

Champ de traçabilité ajouté :
"_reassigned_from": "java-to-python-translator"

5. Étape 2 — Formation des paires (transform.py)

En résumé

Après le nettoyage, chaque record contient des champs source (description, code, question, texte…) à assembler en paires d'entraînement : une paire = une instruction (prompt) + la réponse attendue (completion). Le template à utiliser est défini par pair_strategy dans la config adapter. Trois templates sont disponibles : doc_to_code, code_migration et qa.

Stratégie doc_to_code — Jointure directe (code)

Un record = une paire. La description du code devient le prompt, le code lui-même devient la completion. Utilisé pour les adapters qui génèrent du code depuis une description : python-migration-quality-reviewer, migration-pipeline-orchestrator. Template : config/transforms/doc_to_code.yaml, champs requis : description + code + lang.

Record d'entrée

{
  "description": "Read a CSV file and
    return a list of rows",
  "code": "import csv\ndef read_csv(p):
    with open(p) as f:
        return list(csv.reader(f))",
  "lang": "python"
}

Paire générée

{
  "prompt": "Write python code that
    does the following:

    Read a CSV file and return
    a list of rows.",
  "completion": "import csv\ndef read_csv(p):
    with open(p) as f:
        return list(csv.reader(f))",
  "lang": "python"
}

Template : Write {{lang}} code that does the following:\n\n{{input}} — le champ lang vient du record source via lang_field: lang dans le YAML.

Stratégie code_migration — Jointure par identifiant commun

Pour les données Rosetta Code, chaque tâche existe dans plusieurs langages sous le même nom (task_name). On joint les records Python et Java ayant le même task_name pour créer une paire de migration. C'est la méthode la plus fiable car l'alignement est garanti par la source elle-même.

Records d'entrée

{ "task_name": "fibonacci",
  "lang": "Python",
  "code": "def fib(n): ..." }

{ "task_name": "fibonacci",
  "lang": "Java",
  "code": "public static int fib(int n)..." }

Paire générée

{
  "prompt": "Migrate the following
    Python code to Java.\n\n
    ```Python\ndef fib(n):\n    ...```",
  "completion": "public static int
    fib(int n) { ... }",
  "meta": {
    "task_name": "fibonacci",
    "src_lang": "Python",
    "tgt_lang": "Java"
  }
}

Template : Migrate the following {{src_lang}} code to {{tgt_lang}}.\n\n```{{src_lang}}\n{{input}}\n```

⚠
Limitation : si la source propose plusieurs variantes d'un algorithme dans le même langage, seule la première est utilisée. Les autres sont perdues à cette étape mais peuvent être récupérées par augmentation en étape 1.

Stratégie qa — Paires question/réponse directes

Un record = une paire. La question devient directement le prompt, la réponse devient la completion. Template le plus simple : aucun paramètre requis, optionnellement un champ domain pour adapter le wording. Template : config/transforms/qa.yaml, champs requis : question + answer.

Cas d'usage : support client, FAQ RH, base légale Q&A, documentation technique sous forme de questions fréquentes.

Record d'entrée

{
  "question": "Quel est le délai légal
    de préavis pour un licenciement
    d'un cadre avec 5 ans d'ancienneté ?",
  "answer": "Pour un cadre avec 5 ans
    d'ancienneté, le délai légal de
    préavis est de 3 mois (art. L1237-1
    du Code du travail), sauf convention
    collective plus favorable."
}

Paire générée

{
  "prompt": "Quel est le délai légal
    de préavis pour un licenciement
    d'un cadre avec 5 ans d'ancienneté ?",
  "completion": "Pour un cadre avec 5 ans
    d'ancienneté, le délai légal de
    préavis est de 3 mois (art. L1237-1
    du Code du travail), sauf convention
    collective plus favorable."
}
✓
Template minimaliste : contrairement à doc_to_code (qui nécessite lang), le template qa n'a aucun params_required. L'instruction est la question elle-même — aucun texte d'instruction supplémentaire n'est injecté, ce qui préserve le style naturel des Q&R.

Stratégie semantic_pair_match — Matching cosinus sur descriptions

Contrairement à code_migration (jointure par identifiant commun) ou fuse (matching sur le contenu brut), semantic_pair_match aligne les records bilingues en comparant leurs descriptions en langage naturel. La description de "string concatenation" en Java et en Python ont une haute similarité cosinus parce qu'elles expliquent le même concept — même si les mots exacts et la syntaxe diffèrent. Fichier : agents/semantic_pair_matcher.py. Template : config/transforms/semantic_pair_match.yaml.

Algorithme

  1. Embed toutes les descriptions en un seul batch (espace vectoriel partagé)
  2. Calcul cosinus + boost concept_keywords (+0,05 par keyword commun)
  3. Bijection stricte — un record target ne peut être apparié qu'une seule fois
  4. Vérification software : AST Python côté source, regex Java côté target
  5. Seuil minimum : min_similarity: 0.75 (configurable dans le YAML)

Config semantic_pair_match.yaml

match_by: semantic_description
min_similarity: 0.75
boost_concept_keywords: true
verification:
  source_lang: ast_python
  target_lang: regex_java
bijection: strict
ℹ
Le paramètre concept_keywords dans languages.yaml booste les matches en ajoutant +0,05 par keyword commun entre les deux descriptions. Ex : "concatenation" présent dans les deux → +0,05.
Records sources séparés
JAVA :
{ "description": "La méthode concat()
    ajoute une chaîne à la fin d'une
    autre chaîne en Java",
  "code": "String s = \"Hello\".concat(\" World\");",
  "lang": "java" }

PYTHON :
{ "description": "La concaténation de
    chaînes combine deux strings en Python",
  "code": "s = \"Hello\" + \" World\"",
  "lang": "python" }
Paire bilingue formée
{
  "prompt": "Migrate the following
    Java code to Python.\n\n
    ```Java\nString s =
    \"Hello\".concat(\" World\");\n```",
  "completion": "s = \"Hello\" + \" World\"",
  "source_lang": "java",
  "target_lang": "python",
  "source_desc": "La méthode concat()
    ajoute une chaîne...",
  "target_desc": "La concaténation
    combine deux strings...",
  "similarity": 0.8312,
  "collector_type": "semantic_matched"
}

Note : similarity = cosinus brut + keyword_boost cumulés. Le champ est "similarity" (pas cos_sim) — produit par SemanticPairMatcher.match().

✓
Zéro LLM — 100% déterministe : contrairement à la stratégie fuse qui appelle un LLM pour générer le code cible, semantic_pair_match n'appelle jamais de LLM — il aligne des paires existantes via embedding + cosinus. Résultat reproductible à chaque run à même graine. Coût d'exécution : uniquement les embeddings Bedrock (batch unique).

6. Étape 2bis — Génération LLM (pair_fuser.py)

En résumé

Quand les données source sont monolingues (uniquement du Java, sans équivalent Python natif), pair_fuser.py utilise un LLM pour générer la traduction dans le langage cible. Le LLM est utilisé uniquement pour la génération — toutes les décisions d'acceptation ou de rejet sont prises par software (AST pour Python, regex pour Java, vérification de ratio). Zéro matching cosinus ici : le matching sémantique sur descriptions est le rôle de semantic_pair_matcher.py (section 5).

⚠
Deux composants distincts : pair_fuser.py (génération LLM) et semantic_pair_matcher.py (matching cosinus sur descriptions) font des choses très différentes. Ne pas les confondre. Le choix entre les deux est piloté par le champ pair_strategy dans la config adapter : fuse → pair_fuser, semantic_match → semantic_pair_matcher.

Algorithme pair_fuser — étape par étape

Comment ça fonctionne

  1. Charger les records source_lang depuis processed/clean_raw/
  2. Pour chaque record : construire le prompt de traduction LLM
  3. Appeler le LLM via pipeline/utils/llm.py (temperature=0.1)
  4. Extraire le code généré depuis la réponse (bloc fencé ou texte brut)
  5. Vérification software : ratio longueur (min 0,15 · max 8,0)
  6. Vérification software : syntaxe target_lang (AST Python / regex Java)
  7. Si OK → paire acceptée avec collector_type: "fused"

Paramètres de vérification

CritèreValeur
Ratio min len(completion)/len(source)0,15
Ratio max len(completion)/len(source)8,0
Longueur minimale code généré30 chars
Rate limit entre appels LLM0,2 s

7. Étape 3 — Nettoyage des paires (clean.py)

En résumé

Les paires formées aux étapes 2 et 2bis passent un dernier cycle de nettoyage avant l'entraînement. Cette étape détecte les quasi-doublons au niveau des paires (deux paires qui enseignent la même chose), filtre les paires trop courtes ou déséquilibrées, attribue un score de qualité final, et divise le dataset en deux lots : 90% pour l'entraînement, 10% pour la validation.

1

Déduplication — Exacte + MinHash

Phase exacte : empreinte MD5 sur le couple prompt+completion.

Phase MinHash : compare les séquences de 5 mots consécutifs entre toutes les paires (5-grams). Si deux paires partagent 85%+ de ces séquences, l'une est supprimée. Cette méthode capture les paires quasi-identiques même si quelques mots ont changé.

950→870
Après déduplication exacte + MinHash
2

Règles configurables dans le fichier de config du projet. Elles garantissent que chaque paire est dans la fenêtre de contexte du modèle, équilibrée entre prompt et completion, et ne contient pas de données sensibles.

9. Protection qualité — Stratégie Anti-GIGO

Notre pipeline implémente une défense en profondeur : chaque étape protège contre une menace spécifique. Aucune couche n'est suffisante seule — c'est leur combinaison qui garantit la qualité finale.

10.3 — Exemple d'augmentation réussie (domaine code)

Record source (score 0,72 ≥ seuil augmentation 0,65)
def bubble_sort(arr):
    n = len(arr)
    for i in range(n):
        for j in range(n-i-1):
            if arr[j] > arr[j+1]:
                arr[j], arr[j+1] = arr[j+1], arr[j]
Variant généré — identifier_renaming (AST-vérifié ✓)
def var_0(var_1):
    var_2 = len(var_1)
    for var_3 in range(var_2):
        for var_4 in range(var_2-var_3-1):
            if var_1[var_4] > var_1[var_4+1]:
                var_1[var_4], var_1[var_4+1] = var_1[var_4+1], var_1[var_4]
_aug_type: identifier_renaming — AST-vérifié ✓
Ce qui change : bubble_sort, arr, n, i, j sont remplacés par var_0, var_1… — la logique est identique, seuls les noms changent.
Pourquoi : le modèle ne doit pas associer un algorithme à des noms de variables spécifiques d'une source, mais à sa structure logique.
Ce que ça apporte : robustesse — le modèle apprend à reconnaître et produire des patterns algorithmiques indépendamment des conventions de nommage.
