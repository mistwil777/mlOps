💡
Rappel terminologie — les "plugins" post-LoRA : Ce que tu appelles "plugins", ce sont les adapters (ou adaptateurs). En pratique sur cette plateforme : LoRA adapters et QLoRA adapters. Après entraînement, tu peux soit les fusionner (mlx_lm.fuse) dans le modèle de base pour obtenir un modèle autonome, soit les garder séparés et les charger dynamiquement au moment du serving — c'est le principe du multi-LoRA (un seul modèle de base, N adapters pour N domaines). On y reviendra ci-dessous.
LoRA — Low-Rank Adaptation
Entraîne uniquement deux petites matrices (A et B) par couche ciblée. Le modèle de base est gelé. Le fichier adapter est petit (~ quelques MB).
→ Quand tu as suffisamment de RAM et un dataset propre. Rank 16 recommandé ici.
QLoRA — Quantized LoRA
Même principe que LoRA mais le modèle de base est chargé en 4-bit. Consomme ~40% moins de RAM. Léger compromis de qualité acceptable sur la plupart des tâches.
→ Par défaut sur M4 Pro pour les modèles 14B+. Les configs YAML utilisent toutes des modèles 4-bit.
Adapter fusionné (Merged)
Les poids de l'adapter sont fusionnés dans le modèle de base via mlx_lm.fuse. Produit un modèle standalone prêt à servir. Pas de dépendance à l'adapter au runtime.
→ Delivery client, air-gap deployments, modèle "produit fini".
Multi-LoRA (chargement dynamique)
Un seul modèle de base chargé en mémoire + N adapters swappables selon la requête. Économise de la RAM. Un adapter par projet/domaine.
→ Production multi-projet sur une seule machine. Roadmap Phase 2.

⚙️ Anatomie du backend — ce qui se passe quand tu cliques

Voici la réponse détaillée à ta question : "quand je clique sur Nouveau Projet, que se passe-t-il côté backend ?"

POST /projects — cycle de création d'un projet
1
Validation du formulaire UI → appel API
Le formulaire SvelteKit (projects/new/+page.svelte) envoie un POST /projects avec : nom, domaine, type de tâche, modèle de base sélectionné, description.
Domaines supportés : code, legal, hr, finance, defense, healthcare, sales, compliance, customer-support
2
Création du fichier de config YAML
Le router api/routers/projects.py génère config/projects/{projet_id}.yaml avec les hyperparamètres par défaut du modèle choisi.
Contenu : model_id, domain, task_type, LoRA config (rank, layers, lr), seuils d'évaluation, paths datalake, baseline AWS, blacklist patterns
3
Création des répertoires datalake dédiés
La plateforme initialise l'arborescence isolée du projet dans le datalake.
datalake/projects/{id}/raw/ — espace immuable d'ingestion
datalake/projects/{id}/processed/ — post-nettoyage
datalake/projects/{id}/fine-tuning-ready/ — JSONL prêt pour MLX
4
Insertion en base SQLite
api/db.py insère une ligne dans la table projects avec : id, name, domain, task_type, model_id, created_at.
WAL mode activé → accès concurrent safe · Foreign keys activés · DB : experiments/mlops.db
5
Initialisation de l'index LanceDB vectoriel
Un namespace vide est réservé dans lancedb/{projet_id}/. L'index sera peuplé lors du step RAG build (via rag_index.py).
Embeddings : nomic-embed-text v1.5 via Ollama :11434 — 100% local
6
Réponse → UI affiche le projet dans la liste
L'API retourne l'objet projet créé. SvelteKit redirige vers la page détail du projet.
⚠️
Point de vigilance : pour l'instant, il n'y a pas d'instance de processus dédiée par projet (pas de container, pas de VM). Tout tourne dans le même processus FastAPI. L'isolation est logique (config YAML + répertoires séparés), pas physique. Pour des projets Defense/Juridique ultra-sensibles, on pourrait envisager un namespace réseau séparé ou une instance FastAPI par projet. C'est un point d'architecture à discuter.

Lancer le pipeline de préparation
Aller sur Données → Pipeline. Sélectionner le projet et lancer.
Ce que fait le pipeline automatiquement :
extract.py → extrait des paires (instruction, réponse) depuis les documents, génère le format chat Mistral [INST]{question}[/INST]{réponse}
clean.py → déduplique (MD5 exact + MinHash near-dup), filtre les patterns blacklistés (password, secret, api_key), score chaque paire 0-1 via le modèle local, garde seulement celles > seuil
→ Résultat dans processed/ puis split train/valid dans fine-tuning-ready/
→ Métriques loguées dans MLflow
4
Révision humaine des paires (optionnel mais recommandé)
Aller sur Données → Révision. Valider, rejeter ou corriger les paires générées automatiquement.
Interface de révision : 3 boutons par paire — ✅ Valider · ❌ Rejeter · ✏️ Corriger
Pour le juridique confidentiel : cette étape est critique. Un avocat doit vérifier que la réponse générée est juridiquement correcte.
Les corrections manuelles sont sauvegardées et retournent dans le dataset.
5
Lancer le fine-tuning
Aller sur Entraînement → Lancer. L'estimateur VRAM aide à choisir batch_size et rank.
Config recommandée pour Mistral 7B juridique :
iters: 800, batch_size: 8, learning_rate: 1e-4, lora_rank: 16, lora_layers: 16

Côté backend : POST /runs → lance python -m mlx_lm.lora en subprocess Python 3.11
→ MLflow tracke chaque 100 steps (train_loss, val_loss)
→ L'adapter est sauvegardé dans adapters/cabinet-legal-confidentiel/{run_id}/
→ SSE stream vers l'UI pour voir la loss en temps réel
6
Évaluer le modèle
Aller sur Test → Playground. Tester des questions réelles, comparer avec la baseline.
Métriques calculées : ROUGE-L (similarité de texte), pass_rate (% de réponses valides), latence p50/p99
Comparaison optionnelle vs AWS Nova Pro (baseline) — uniquement pour calibrage, jamais en prod client
Seuils à atteindre : pass_rate ≥ 0.85, rouge_l ≥ 0.65, latence ≤ 2× baseline
7
Déployer ou livrer le modèle
Aller sur Livraison. Choisir entre "Servir localement" ou "Exporter".
Option A — Servir on-premise : mlx_lm.server sur port configuré → API OpenAI-compatible → le cabinet intègre dans son outil interne
Option B — Package ZIP livrable : télécharger le modèle fusionné (base + adapter) ou l'adapter seul pour déploiement air-gap sur la machine du client

Côté backend : mlx_lm.fuse fusionne les poids, sanity check avec prompts génériques, rollback automatique si échec

🔭 Recommandations & Points ouverts — ma lecture critique

⚠️ Isolation physique par projet — à discuter

Aujourd'hui, l'isolation est logique : des répertoires séparés et des configs YAML distinctes, mais tout tourne dans le même processus FastAPI et la même DB SQLite. Pour des projets Defense et Juridique simultanés sur la même machine, c'est un risque d'audit : un bug dans le router data.py pourrait théoriquement accéder au mauvais projet.

Option : une instance FastAPI par projet sensible, chacune sur son port. Ou namespace SQLite séparé. Trade-off : complexité opérationnelle vs garantie d'isolation.

🧪 Métriques domaine-spécifiques manquantes

Le fichier pipeline/utils/metrics.py couvre ROUGE-L et CodeBLEU. Pour le juridique, il manque : BLEU légal, cohérence sémantique des arguments, détection de contradiction. Pour la défense : F1 classification, FPR, recall sur classes critiques.

Recommandation : créer un fichier metrics_{domaine}.py par domaine, chargé dynamiquement depuis le YAML du projet. Le skill /eval-model doit être étendu.

💾 Capitalisation — skills & scripts comme actifs

Chaque script fonctionnel est de la donnée réutilisable. Les skills CC (/train-lora, /eval-model, etc.) sont des actifs à versionner au même titre que les adapters. Actuellement, les skills ne sont pas dans le suivi DVC — ils sont dans .claude/ uniquement.

Recommandation : versionner les skills dans config/skills/ ou skills/ dans le repo git. Un skill parfaitement fonctionnel est aussi précieux qu'un adapter de qualité.

✅ Multi-LoRA — brique à anticiper

La roadmap Phase 2 prévoit multi-LoRA. C'est la clé pour faire coexister "cabinet-legal" et "rafale-vision" sur la même machine sans doubler la consommation RAM : un seul Mistral 7B en mémoire, deux adapters swappés selon le projet appelant.

Prérequis : le registre adapters.py existe déjà. Il faut ajouter la logique de routing dans playground.py et le serving multi-adapter dans le models.py.

🔁 Boucle de ré-entraînement — feedback loop

Aujourd'hui, un utilisateur qui corrige une réponse du modèle en production ne réinjecte pas automatiquement cette correction dans le dataset. C'est de la valeur perdue.

Recommandation : ajouter un endpoint "feedback en production" qui enregistre les corrections dans datalake/projects/{id}/feedback/ et les intègre au prochain cycle de nettoyage. C'est la boucle vertueuse de l'amélioration continue.

📊 Dashboard temps réel — observable mais pas encore live

Le frontend existe avec les composants LossChart, MetricCard, ProgressRing. Le SSE est câblé pour les jobs longs. Mais le dashboard principal agrège depuis SQLite par polling — pas en temps réel.

Recommandation : pousser les événements clés (run terminé, eval passée, modèle déployé) via SSE au dashboard. Cela donnerait une vraie expérience "control tower" sans infrastructure supplémentaire.
