Objet : Autorisation d'accès à des ressources techniques externes nécessaires au téléchargement de modèles d'IA et de bibliothèques de Machine Learning, dans le cadre du projet MLOps de production de modèles de langage locaux (souverains, sans inférence cloud en production). Les accès demandés sont unidirectionnels en lecture seule (téléchargement), limités à la phase de développement, et ne transportent aucune donnée client ni donnée classifiée.

1. Contexte du projet

Le projet MLOps IA Souveraine a pour objectif de produire des modèles de langage (LLM) fine-tunés localement, déployables en environnement client on-premise ou air-gapped. L'infrastructure vise une souveraineté totale : zéro appel cloud en production, 100 % inférence locale.

La machine de développement est un MacBook Pro M4 Pro 48 Go (macOS Tahoe 26.4). Le fine-tuning utilise le framework MLX-LM (Apple Silicon), la vectorisation Qdrant, et le serving local Ollama.

Plusieurs composants essentiels du pipeline nécessitent un accès réseau unique lors de leur installation initiale afin de télécharger les artefacts binaires (poids de modèles, bibliothèques compilées). Une fois téléchargés, ces artefacts sont utilisés exclusivement en local.

3bis. Nouveaux blocages identifiés — mise à jour 4 juin 2026

⚠ Escalade : ZScaler bloque désormais le partage de connexion mobile

En l'absence de whitelist, le développeur a tenté de contourner le blocage réseau Capgemini en utilisant un partage de connexion 4G depuis son téléphone personnel (procédure standard de développement hors-bureau). ZScaler intercepte et bloque également cette connexion, empêchant tout accès aux ressources techniques listées ci-dessus même via un réseau extérieur à l'infrastructure Capgemini.

Conséquence directe : le développeur ne peut pas télécharger les modèles d'IA nécessaires par aucun moyen depuis son poste de travail Capgemini, quelle que soit la connexion réseau utilisée. L'avancement du projet MLOps est bloqué depuis le 2 juin 2026.

3bis.1 — SearXNG (moteur de recherche interne auto-hébergé)

Pour réduire la dépendance aux APIs externes et respecter les principes de souveraineté, l'équipe a déployé SearXNG — un méta-moteur de recherche 100 % open-source auto-hébergé dans Docker sur le poste local. SearXNG agrège Google, Bing, DuckDuckGo et GitHub en un seul appel interne, sans transmettre de données à des tiers au-delà des requêtes de recherche standard.

ZScaler bloque les requêtes HTTPS sortantes du container Docker vers les moteurs de recherche en injectant son certificat SSL, ce qui cause des erreurs SSL: CERTIFICATE_VERIFY_FAILED à l'intérieur du container. Le service SearXNG démarre correctement mais ne peut retourner aucun résultat.

Domaine / URL Usage Type Protocole
*.google.com Moteur de recherche — agrégation SearXNG Recherche HTTPS/443
*.bing.com Moteur de recherche — agrégation SearXNG Recherche HTTPS/443
html.duckduckgo.com Moteur de recherche — agrégation SearXNG + fallback direct Recherche HTTPS/443
api.search.brave.com API Brave Search — fallback lorsque DuckDuckGo rate-limite (gratuit, 2000 req/mois) Recherche HTTPS/443
Contexte technique : Ces accès ne servent qu'à la découverte de sources de documentation publiques (tutoriels Java/Python sur baeldung.com, programiz.com, docs.oracle.com...) utilisées comme données d'entraînement. Aucune donnée interne n'est transmise. Les requêtes sont du type "jpa java tutorial code example" — strictement des recherches de documentation technique publique.

Erreur observée dans les logs Docker (4 juin 2026) :
ssl.SSLCertVerificationError: [SSL: CERTIFICATE_VERIFY_FAILED] certificate verify failed: unable to get local issuer certificate
Le certificat ZScaler n'est pas présent dans le trust store du container SearXNG.

3bis.2 — Partage de connexion mobile (nouveau blocage)

ZScaler est configuré pour s'appliquer sur le poste de travail indépendamment de l'interface réseau active. Le client ZScaler installé sur le MacBook Pro intercepte les connexions HTTPS même lorsque le poste est connecté via partage de connexion 4G/5G personnel, hors du réseau Capgemini.

Ce comportement est inhabituel et va au-delà de la politique de filtrage standard qui s'applique typiquement au réseau d'entreprise uniquement. Il empêche tout contournement temporaire en dehors des horaires ou des locaux Capgemini.

Impact opérationnel : Le développeur ne dispose d'aucun moyen de télécharger les artefacts techniques requis (modèles ~8 Go, bibliothèques ML) depuis son poste de travail Capgemini, quel que soit le réseau utilisé. Le seul contournement actuel est d'utiliser un ordinateur personnel distinct, ce qui contrevient aux règles de sécurité Capgemini sur la séparation des environnements de travail. La situation est bloquante sans issue technique acceptable.

Note sur la catégorie Zscaler bloquée : La catégorie « Generative AI and ML Applications » inclut des dépôts d'artefacts techniques (poids de modèles, bibliothèques compilées) qui ne sont pas des outils d'IA en ligne (ChatGPT, Copilot, etc.). Les accès demandés correspondent à des registres de téléchargement technique (équivalents à Docker Hub ou npm) et non à des services de génération d'IA en ligne.
