Audit de Situation Complet - Projet MLOps Migrator

Cartographie exhaustive, verification croisee des donnees, identification des problemes bloquants et plan d'action pour le projet de fine-tuning local destine a la migration Java vers Python.

Resume executif - Alerte critique

Le projet ne peut PAS entrainer un modele de migration Java vers Python en l'etat. Sur 2 800 paires prates pour le fine-tuning, zero est une veritable paire de traduction Java vers Python. Toutes les paires actuelles sont de type doc_to_code monolingue Python ("Write python code..."). Trois problemes critiques bloquent la production : (1) incoherence de direction dans la configuration, (2) absence totale de paires bilingues malgre 505 taches Rosetta Code matchables, (3) le pair_fuser n'a jamais ete execute pour les adapters qui le requierent.

4. Problemes identifies

4.1 Problemes CRITIQUES (bloquants)

P1 - Incoherence de direction dans la configuration

SourceDitDirection implicite
Adapter names (migrator.yaml)"java-to-python-translator"Java -> Python
Adapter descriptions"recoit en entree le corps Java... genere un fichier Python"Java -> Python
CLAUDE.md"Current scope: Migrator (Python->Java migration)"Python -> Java
config/languages.yaml (python-java)source_lang: python, target_lang: javaPython -> Java
migrator.yaml transform.paramssrc_lang: python, tgt_lang: javaPython -> Java
User brief"migration Java->Python"Java -> Python

Impact : Si le pair_fuser etait lance en l'etat, il prendrait les records Python et genererait du Java. Le modele apprendrait a traduire Python vers Java = l'inverse de l'objectif.

Correction : Ajouter un entry java-python dans languages.yaml avec source_lang=java, target_lang=python. Modifier migrator.yaml transform.params : src_lang=java, tgt_lang=python.

P2 - Pair_fuser jamais execute sur les 4 adapters fuse

Les 4 adapters avec pair_strategy: fuse representent 3 560 paires cibles (73% du total). Aucun n'a ete fuse. Les paires presentes dans processed/pairs/ pour ces adapters sont des paires doc_to_code erronees, generees par le mauvais chemin du pipeline.

Impact : Pas d'entrainement possible sur le coeur du projet (traduction de code).

P3 - Donnees fine-tuning-ready = 100% monolingue Python, inutilisables

Les 2 800 paires dans fine-tuning-ready/ sont toutes du format :

{"prompt": "Write python code that does the following:\n\n[description]", "completion": "[code Python]"}

Un modele entraine sur ces donnees apprendrait a generer du Python depuis une description anglaise, pas a migrer du Java vers du Python.

4.2 Problemes MAJEURS (non bloquants mais degradants)

P4 - Desequilibre Python/Java dans le corpus brut

Ratio Python:Java = 7.3:1 (13 598 vs 1 862). Pour un modele de traduction Java->Python, on a besoin de plus de code Java en entree (source) que de code Python (cible, qui peut etre genere). Le corpus est domine par la documentation Python ce qui est l'inverse du besoin.

P5 - Paires manuelles annoncees mais absentes

La configuration declare 810 paires manuelles au total :

  • python-migration-quality-reviewer : 360 paires manuelles
  • spring-config : 250 paires manuelles
  • jpa-hibernate : 200 paires manuelles

Aucune n'a ete fournie. Le collecteur manual dans le registry a module: null.

P6 - clean_raw ne preserve pas assez de records Java

Sur 8 199 records bruts pour java-to-python-translator, seuls 990 survivent au clean_raw. Parmi ceux-ci, seulement 4 sont en Java. Le filtre heuristique est calibre pour le code Python (validation AST Python, mots-cles Python) et penalise systematiquement les records Java.

P7 - Modele ZScaler-bloque non telecharge

Le modele cible Qwen2.5-Coder-14B-Instruct-4bit n'est pas disponible localement. Le proxy ZScaler bloque les telechargements HuggingFace. Le pair_fuser a besoin d'un LLM pour generer les traductions (meme si la decision d'acceptation est software-only).

4.3 Problemes architecturaux

P8 - Pipeline clean.py deconnecte du multi-adapter

Le fichier pipeline/clean.py (DataCleaner) lit depuis raw/pairs_raw.jsonl — un seul fichier. Il ne connait pas la structure multi-adapter et ignore les fichiers per-adapter dans processed/pairs/. Il devrait agreger tous les fichiers de pairs/ par adapter.

P9 - Absence de verifieur Java dans pair_fuser

Le pair_fuser a un verifieur Python (AST parse) et un verifieur Java (regex heuristique : mots-cles + accolades equilibrees). Le verifieur Java est beaucoup moins fiable que le Python. Pour un projet centre sur la generation de Python depuis Java, c'est le verifieur Python qui est critique (verification du code genere) = correct. Mais le verifieur Java est trop basique pour valider le code source d'entree.

6. Ce qui fonctionne bien

6.1 Composants solides - ne pas toucher

Architecture agnostique du pipeline

Le design est config-driven et sans hardcode projet/langue. Les collecteurs produisent des records neutres ({task_name, lang, code} ou {description, code, lang}), les templates de transformation sont parametriques, le registry de collecteurs est extensible YAML-only. Ajouter un nouveau projet ou une nouvelle paire de langues ne necessite aucune modification de code Python.

Collecteurs bien implementes

  • rosetta_collector : extraction propre du wikitext MediaWiki, gestion rate-limit, dedup au write
  • doc_collector : crawl BFS avec profondeur limitee, skip patterns, extraction Shiki/hljs/Pygments, mode Playwright anti-bot
  • Registry-based dispatch : ajout de collecteur = 1 entry YAML, zero code

Pipeline clean_raw sophistique

7 etapes bien sequencees : exact dedup, heuristic scoring, semantic dedup, relevance scoring, volume control, coverage clustering, cross-adapter reassignment. Augmentation CV-inspired (identifier renaming, loop style swap, desc paraphrase). Logique sound, juste le calibrage des seuils Java a ajuster.

Pair_fuser bien concu

Design correct : LLM pour la generation uniquement, toute decision d'acceptation par software (AST parse, ratio verification). Rate limiting, extraction robuste de code blocks, parametrage via languages.yaml. Il suffit de corriger la direction et de le lancer.

API et UI completes

L'API FastAPI couvre tout le workflow : collect, fuse, review, pipeline, health, lineage, search, browse. Le frontend SvelteKit offre 6 onglets (Sante, Collecte, Ingestion, Pipeline, Controle qualite, Recherche). Endpoints SSE pour le suivi temps reel des jobs.

Green IT et souverainete

  • Zero appel cloud en inference production (MLX local / Ollama)
  • Embeddings cascade : Ollama > Bedrock > TF-IDF (graceful degradation)
  • Batch size optimise pour M4 Pro 48GB
  • Reuse des configs, pas de redondance

6.2 Decisions architecturales correctes

Multi-adapter par projet

6 adapters specialises plutot qu'un monolithe. Chaque adapter a un perimetre precis, des sources de donnees dediees, et un role clair dans le pipeline de migration.

Separation generation / validation

Le pair_fuser genere via LLM mais accepte/rejette via software deterministe. Le quality_reviewer valide la qualite semantique. Bonne separation des responsabilites.

Collecte naturelle > generation

Priorite aux sources naturellement bilingues (Rosetta Code, repos bilingues) plutot qu'a la generation synthetique LLM. Le LLM n'intervient que quand les sources naturelles sont insuffisantes (strategie fuse).

Immutabilite du raw/

Les fichiers raw sont timestampes et jamais ecrases. Lineage complete tracee en SQLite. Audit trail intact pour la compliance Defense.
