01 — Contexte

Finalité de la plateforme et deux contextes distincts

La plateforme MLOps Capgemini est une chaîne de production et de qualification d'adapters LoRA spécialisés. Elle ingère des données métier, entraîne des adapters locaux sur ces données, les qualifie via un gate de déploiement, et les livre au client sous forme d'un bundle Docker autonome. Les adapters sont la propriété intellectuelle de Capgemini — c'est notre valeur différenciante. Le modèle de base (open source) n'est pas notre propriété.

Contexte 1 — Plateforme MLOps Capgemini
Finalité : Collecter, nettoyer, entraîner, évaluer, qualifier les adapters LoRA
Où ça tourne : Directement sur la machine (pas de Docker pour ces étapes — MLX nécessite l'accès direct au hardware Apple Silicon)
Outils : MLX-LM (fine-tuning), Qdrant (RAG entraînement), MLflow (tracking interne), SQLite (métadonnées)
Livrable produit : Une bibliothèque d'adapters qualifiés, prêts à être embarqués dans le bundle client
MLflow : Outil Capgemini interne uniquement — jamais livré au client
Contexte 2 — Bundle livrable client
Finalité : Inférence autonome chez le client — docker compose up, c'est tout
Où ça tourne : Infrastructure Linux du client (on-premise ou serveur dédié)
Contient : Ollama (sert le modèle de base + charge les adapters), Qdrant (index RAG pré-chargé), orchestrateur de routage
Ne contient PAS : MLflow, les outils de fine-tuning, les données d'entraînement brutes
Zéro cloud : Tout fonctionne en local, sans appel réseau externe
🧩
Les adapters : notre IP
Un adapter LoRA est un delta de poids appliqué dynamiquement au modèle de base. Plusieurs adapters coexistent par projet — appelés sélectivement selon la tâche. C'est notre valeur, pas le modèle de base.
🏗️
Fine-tuning sans Docker
MLX (Apple Silicon) exige un accès direct au hardware — pas de virtualisation. Les étapes de collecte, nettoyage, entraînement et évaluation tournent directement sur la machine, sans conteneur.
🔐
Isolation par construction
Chaque projet est une bulle étanche : données, base de données, logs, adapters, index RAG. Aucun flux inter-projet n'est possible par construction — isolation physique (OS), pas seulement logique.
📦
Livrable Docker autonome
Le bundle client est un Docker Compose contenant Ollama, Qdrant et l'orchestrateur. Les vecteurs RAG sont pré-chargés au moment de l'export. Le client n'a qu'une commande à lancer.
02 — Flux détaillé

Ce qui se passe quand on crée un nouveau projet

L'opérateur clique sur « Nouveau projet » dans le dashboard et remplit le formulaire. Voici exactement ce qui se produit, couche par couche, jusqu'à ce que le projet soit prêt à recevoir des données.

1
Saisie dans le dashboard (SvelteKit) Frontend
L'opérateur renseigne : nom du projet, description, domaine métier, modèle de base cible, et surtout le niveau de classification (interne | confidentiel | secret). Ce choix conditionne tous les comportements de sécurité décrits dans ce document.

Le dashboard envoie un POST /api/projects au backend FastAPI.
2
Validation & génération de l'identifiant API FastAPI — projects.py
Le backend :
  • Vérifie que le domaine et le type de tâche sont dans les listes autorisées
  • Génère l'identifiant : project_id = nom.lower().replace(" ", "-") — c'est la clé de tous les chemins qui suivent
  • Vérifie qu'aucun projet avec cet ID n'existe déjà pour éviter tout écrasement accidentel
3
Écriture du fichier de configuration YAML Filesystem
Crée config/projects/<project_id>.yaml — fichier maître du projet. Il contient :
  • Nom, description, domaine, niveau de classification
  • Modèle de base cible (ex. mistral-7b-instruct-4bit)
  • Liste des adapters du projet et leurs tâches associées
  • Chemin de l'index Qdrant dédié : qdrant/collections/<project_id>
  • Chemins datalake : datalake/projects/<project_id>/{raw,processed,fine-tuning-ready}/
  • Seuils de qualité que chaque adapter devra dépasser avant déploiement
4
Création de l'arborescence datalake Filesystem
Crée sur le disque les trois répertoires du cycle de vie de la donnée : 
datalake/projects/<project_id>/
├── raw/               # données brutes — IMMUTABLES après ingestion
│   └── feedback/      # retours humains pour réentraînement futur
├── processed/         # données après nettoyage et validation
└── fine-tuning-ready/ # paires JSONL prêtes pour mlx_lm.lora
Ces chemins sont construits à partir du project_id et ne contiennent aucune référence à d'autres projets. Il n'existe ni lien symbolique ni redirection vers d'autres répertoires.
5
Création de la base de données SQLite dédiée Base de données
Le backend crée experiments/projects/<project_id>/mlops.db — un fichier SQLite exclusif à ce projet, initialisé avec le schéma complet :
  • runs — historique de tous les entraînements : hyperparamètres, loss, durée, statut, adapter associé
  • adapters — bibliothèque d'adapters produits : nom, tâche, version, chemin, statut (staging/production)
  • datasets — versionnage du datalake (nombre de paires, qualité moyenne, chemin)
  • evaluations — métriques d'évaluation post-entraînement (BLEU, ROUGE-L, taux de réussite, latence)
  • rag_feedback — retours des utilisateurs sur les réponses RAG
  • archived_runs — corbeille des runs supprimés (soft-delete, récupérable)
Conséquence directe : il est physiquement impossible d'accéder aux données d'un autre projet via une requête SQL — les bases sont des fichiers OS distincts, sans tables croisées.
6
Enregistrement d'une expérience MLflow dédiée MLflow Tracking — Capgemini interne
Crée une expérience MLflow nommée <project_id>-lora. Pour les projets confidentiel ou secret, cette expérience est créée dans l'instance MLflow dédiée au projet (port isolé, pas l'instance partagée). Tous les runs d'entraînement ultérieurs y sont loggés — courbes de loss, hyperparamètres, métriques finales.

MLflow est un outil Capgemini interne — il ne fait pas partie du bundle livré au client.
7
Initialisation de l'index Qdrant dédié Qdrant RAG
Une collection Qdrant nommée <project_id> est créée dans l'instance locale. Cet index vectoriel est utilisé à la fois pendant l'entraînement (augmentation contextuelle des paires) et sera exporté dans le bundle client. Une requête de similarité sur la collection du projet A ne peut structurellement pas atteindre les vecteurs du projet B.
8
Création du répertoire d'adapters Filesystem
Crée adapters/<project_id>/ — emplacement de tous les checkpoints LoRA produits pour ce projet. Chaque run d'entraînement crée un sous-répertoire adapters/<project_id>/<run_id>/ contenant les poids de l'adapter, la configuration et le rapport d'évaluation.
9
Le projet est prêt Dashboard
Le dashboard affiche le projet dans la liste avec son statut, son niveau de classification et ses ressources allouées. L'opérateur peut maintenant déposer des données, lancer un entraînement, consulter les métriques, gérer la bibliothèque d'adapters.

Propriété fondamentale
À aucun moment un chemin de fichier associé à projet-alpha ne contient ou ne référence le chemin de projet-beta. L'isolation est physique (chemins OS distincts) et non seulement logique (filtres SQL). Une lecture directe du disque par un tiers ne mélange pas les projets.
Adapters vs modèle fusionné
Adapter : poids LoRA légers (~quelques Mo), chargés dynamiquement sur le modèle de base. Plusieurs adapters par projet, appelés selon la tâche. Notre IP, livré dans le bundle client.
Modèle fusionné (fused) : résultat de mlx_lm.fuse qui intègre les poids de l'adapter dans le modèle de base. Utilisé uniquement pour le gate de déploiement — jamais servi directement en production Capgemini, non inclus dans le bundle client. Le client reçoit le modèle de base + les adapters séparément, Ollama gère le chargement dynamique.
04 — Classification

Comportement complet selon le niveau de sensibilité

Le niveau de classification est choisi à la création du projet. Il déclenche automatiquement les mesures ci-dessous sans intervention manuelle supplémentaire.

INTERNE
Usage typique : R&D Capgemini, projets pilotes, données non sensibles
Fine-tuning : accès direct hardware Apple Silicon — pas de contrainte réseau
MLflow : instance partagée ou dédiée selon configuration
Accès données UI : complet (lecture + export)
SQLite : fichier isolé par projet
Bundle export : standard
CONFIDENTIEL
Usage typique : données client sensibles, projets Défense non classifiés au sens réglementaire
Fine-tuning : isolation réseau — aucune connexion sortante autorisée pendant l'entraînement
MLflow : instance dédiée sur port isolé — pas d'accès externe
Accès données UI : lecture restreinte, export désactivé
SQLite : fichier isolé + permissions OS 600
Bundle export : chiffrement recommandé
SECRET
Usage typique : données classifiées Défense — Secret Défense, données souveraines
Fine-tuning : isolation maximale — tout accès réseau bloqué au niveau OS pendant l'entraînement
MLflow : instance dédiée, aucune API externe — forcé automatiquement
Accès données UI : aucun accès aux données source — métriques agrégées uniquement. Capgemini ne voit pas les données.
SQLite : fichier isolé + chiffrement (SQLCipher)
Bundle export : désactivé par défaut — validation manuelle Capgemini + client requise
Principe SECRET — responsabilité client totale sur les données
Pour un projet classifié SECRET, Capgemini n'accède jamais aux données source. Le client apporte ses données, les dépose dans le répertoire raw/ de son projet sur la machine d'entraînement, et supervise le pipeline depuis sa propre interface. Les données ne transitent pas par les systèmes Capgemini. La plateforme MLOps est un outil d'exécution — elle produit les adapters sans consulter le contenu qu'elle traite. Ce principe doit être contractualisé avant le début du projet.
Note pour l'équipe Cyber
Le forçage de l'isolation réseau en cas de classification confidentiel ou secret est implémenté dans les scripts de lancement et ne peut pas être contourné depuis l'UI. Un warning est émis et tracé à chaque forçage automatique. La résistance à ce forçage nécessiterait une modification directe des scripts — action traçable via git.

06 — Cycle de vie

Pipeline complet d'un projet, de l'ingestion à la livraison

Toutes les étapes 1 à 8 se déroulent sur la plateforme Capgemini, directement sur la machine (sans Docker). L'étape 9 est le gate de qualification des adapters. L'étape 10 produit le bundle livrable client.

Étape Déclencheur Ce qui est créé ou modifié Isolation
1. Création projet Dashboard → Nouveau projet YAML config, datalake dirs, SQLite dédiée, collection Qdrant, répertoire adapters Complète
2. Ingestion données /extract-pairs project=<id> datalake/projects/<id>/raw/ — IMMUTABLE après ingestion Complète
3. Nettoyage & validation /clean-dataset project=<id> datalake/projects/<id>/processed/ Complète
4. Augmentation synthétique /augment-dataset project=<id> Paires générées ajoutées à processed/ Complète
5. Ingestion RAG POST /api/rag/<id>/ingest Vecteurs indexés dans la collection Qdrant <id> Complète
6. Fine-tuning LoRA /train-lora project=<id> adapter=<nom> Adapter dans adapters/<id>/<adapter-nom>/ + run loggé dans SQLite & MLflow dédiés Complète
7. Évaluation adapter /eval-model project=<id> adapter=<nom> Métriques dans SQLite dédiée, comparaison vs baseline configurée Complète
8. Gate de déploiement scripts/deploy_gate.py --project <id> --adapter <nom> Vérifie métriques MLflow vs seuils du YAML projet — bloque si insuffisant. Adapter promu en production dans la DB. Complète
9. Composition bibliothèque Dashboard → Gérer les adapters Sélection des adapters qualifiés à inclure dans le bundle, affectation des tâches, test de routage Complète
10. Export bundle client scripts/export_bundle.sh <id> Bundle Docker autonome : Ollama + adapters + Qdrant snapshot + orchestrateur + MANIFEST.sha256 Complète

Le gate de déploiement — barrière qualité par adapter

Aucun adapter ne peut être promu et inclus dans le bundle sans passer le gate. Le script scripts/deploy_gate.py lit les seuils qualité définis dans le YAML du projet et les compare aux métriques enregistrées dans l'instance MLflow dédiée :

MétriqueSignificationSens
pass_rateTaux de réussite des cas de test fonctionnels de l'adapterValeur minimale — configurable par projet et par adapter
rouge_lSimilarité séquentielle avec les références attenduesValeur minimale — configurable par projet
latency_ratioLatence de l'adapter rapportée à la baselineValeur maximale — l'adapter ne doit pas dégrader significativement la vitesse
compilation_rateTaux de code généré syntaxiquement valideOptionnel — activé selon le domaine de l'adapter

Si un seuil n'est pas atteint, le gate bloque la promotion, retourne la liste des critères en échec, et l'adapter reste en staging — il n'est pas inclus dans le bundle.

07 — Bundle livrable client

Ce que contient le bundle Docker autonome

Le bundle est un Docker Compose que le client dépose sur son infrastructure Linux et démarre avec docker compose up. Il est entièrement autonome — aucune connexion réseau externe n'est requise, aucun outil Capgemini n'est embarqué. Les vecteurs RAG sont pré-chargés au moment de l'export.

Ollama port 11434
Rôle : Serveur d'inférence local
Ce qu'il fait : Sert le modèle de base et charge dynamiquement les adapters LoRA selon la requête entrante. API compatible OpenAI.
Modèle de base : Open source (ex. Mistral 7B) — pas la propriété Capgemini. Téléchargé une fois dans l'image.
Adapters : Chargés depuis le volume /adapters/ — notre IP. Plusieurs adapters coexistent, l'orchestrateur choisit lequel activer.
Pourquoi Ollama : Gestion native des adapters LoRA, format GGUF/MLX, tourne sur Linux, zéro configuration supplémentaire.
Qdrant port 6333
Rôle : Index vectoriel RAG de production
Ce qu'il fait : Sert les recherches sémantiques en temps réel pour enrichir le contexte des requêtes (RAG).
Données : Snapshot Qdrant exporté depuis la plateforme Capgemini au moment de la livraison — vecteurs pré-chargés.
Seul outil vectoriel : Qdrant est utilisé à la fois en développement (plateforme Capgemini) et en production (bundle client). Pas de LanceDB.
Volume monté : /qdrant-data/ — persistant entre redémarrages.
Orchestrateur de routage port 8080
Rôle : Point d'entrée unique des requêtes client
Ce qu'il fait : Reçoit la requête, analyse l'intention, sélectionne le ou les adapters à activer, interroge Qdrant si nécessaire, synthétise la réponse.
Routage multi-adapter : Plusieurs adapters peuvent être appelés en séquence ou en parallèle selon la complexité de la tâche.
Configuration : Définie dans le YAML du projet, embarquée dans le bundle — le client ne la modifie pas.
Ce que le bundle ne contient PAS
MLflow — outil Capgemini interne uniquement. Le client n'a pas accès au tracking d'expériences. Les données d'entraînement brutes — restent sur l'infrastructure Capgemini. Les scripts de fine-tuning — idem, infrastructure Capgemini. Les modèles fusionnés (fused) — le bundle contient le modèle de base + les adapters séparés, pas un modèle monolithique fusionné.

Déploiement côté client

# Infrastructure cible client : Linux (Ubuntu 22.04+, Debian 12+, RHEL 9+)
# Prérequis : Docker Engine + Docker Compose v2

# Livraison du bundle
scp bundle-projet-alpha-20260429.tar.gz client@serveur:/opt/capgemini/

# Démarrage — c'est tout ce que le client fait
tar xzf bundle-projet-alpha-20260429.tar.gz
cd bundle-projet-alpha-20260429/
docker compose up -d

# Vérification d'intégrité avant démarrage (optionnel)
shasum -a 256 -c MANIFEST.sha256
Souveraineté complète chez le client
Une fois livré, le bundle fonctionne sans aucune connexion à Capgemini ni à Internet. Le client est propriétaire de son instance, peut l'auditer, la sauvegarder, la répliquer. Aucune télémétrie, aucun callback. La souveraineté des données est totale.
08 — Garanties de sécurité

Ce que la plateforme garantit

🗂️
Isolation physique des données
Chaque projet a son propre répertoire dans le datalake, construit à partir de son identifiant. Une validation path traversal sur chaque requête API interdit les accès ../autre-projet.
🗄️
Base de données par projet
Chaque projet a son propre fichier SQLite. Il est physiquement impossible d'accéder aux métadonnées d'un autre projet via une requête SQL — les bases n'ont aucune table en commun.
🧩
Adapters isolés par projet
Les adapters LoRA sont stockés sous adapters/<project_id>/. Un adapter d'un projet ne peut pas être chargé par l'orchestrateur d'un autre projet — le chemin est hardcodé par projet.
📋
Index RAG dédié (Qdrant)
Chaque projet a sa propre collection Qdrant. Deux collections Qdrant distinctes sont physiquement incapables de se croiser lors d'une recherche de similarité. Qdrant est l'unique moteur vectoriel — en développement comme en production.
🔬
MLflow interne uniquement
MLflow est un outil Capgemini de tracking d'expériences. Il n'est jamais livré au client, n'expose aucune API externe, et tourne sur port isolé pour les projets confidentiels et secrets.
🔒
Gate obligatoire avant bundle
Un adapter ne peut jamais être inclus dans le bundle client sans avoir passé le gate de qualité. La promotion est bloquée si les métriques ne sont pas atteintes.
🚫
Zéro appel cloud en production
L'inférence en production est 100 % locale via Ollama. Le bundle client fonctionne en réseau totalement fermé. Aucune donnée client ne transite par un service tiers.
📦
Bundle vérifiable
Le script export_bundle.sh génère un MANIFEST.sha256 listant le hash de chaque fichier. Le client peut vérifier à tout moment qu'aucun fichier n'a été modifié depuis la livraison.
Pour l'armée française — Secret Défense
Un projet classifié secret active automatiquement l'isolation maximale : aucun accès réseau pendant le fine-tuning, MLflow dédié sans API externe, aucun accès aux données source depuis le dashboard Capgemini, SQLite chiffré. La plateforme MLOps n'a aucune télémétrie, aucun callback vers Capgemini ou un tiers. Les données classifiées ne quittent jamais le périmètre physique de la machine d'entraînement. Capgemini produit les adapters sans jamais avoir accès au contenu des données d'entraînement.
09 — Auditabilité

Traçabilité et audit

La plateforme maintient une traçabilité complète de toutes les actions, accessible par projet.

Ce qui est tracé automatiquement

  • Chaque run d'entraînement : hyperparamètres, durée, loss, adapter cible, statut final
  • Chaque évaluation : métriques obtenues, comparaison vs baseline
  • Chaque passage au gate : critères passés, critères bloquants, horodatage, adapter concerné
  • Chaque promotion d'adapter en production : version, date, opérateur
  • Chaque ingestion de données : volume, hash SHA-256, source
  • Chaque export de bundle client : contenu, date, hash MANIFEST
  • Actions de l'assistant IA (Claude Code) : outil utilisé, commande, session ID

Comment auditer un projet

  • SQLite projet : experiments/projects/<id>/mlops.db
  • MLflow dédié : instance locale Capgemini — non accessible au client
  • Logs entraînement : logs/<project_id>/
  • Audit IA : .claude/audit.log
  • Historique git : chaque modification de config est versionnée
  • MANIFEST bundle : bundles/<id>-<date>/MANIFEST.sha256

Vérification d'intégrité du bundle livré

Le script d'export génère un fichier MANIFEST.sha256 listant le hash SHA-256 de chaque fichier du bundle. Le client peut vérifier à tout moment qu'aucun fichier n'a été modifié depuis la livraison :

# Vérifier l'intégrité du bundle livré
shasum -a 256 -c bundle-projet-alpha-20260429/MANIFEST.sha256

Ce que la plateforme ne fait pas

  • Aucune télémétrie vers Anthropic, Capgemini central, ou tout tiers
  • Aucune copie de données clients dans le cloud
  • Aucun adapter d'un projet n'est réutilisé ou partagé avec un autre projet
  • Aucun entraînement sur les données d'un projet ne bénéficie à un autre
  • MLflow n'est jamais exposé au client ni embarqué dans le bundle
  • Aucun modèle fusionné (fused) n'est servi ou livré — uniquement le modèle de base + adapters séparés
Conformité
