RAG, fine-tuning, ou les deux ? Un guide pratique pour choisir la bonne stratégie selon le contexte — avec des exemples tirés de missions réelles.

Le problème

Nous payons des providers pour du contexte que nous possédons déjà

Aujourd'hui, quand une équipe envoie un prompt à ChatGPT ou GitHub Copilot, elle paie pour deux choses : la capacité de raisonnement du modèle (comprendre la demande, générer du texte cohérent) et la mémoire (connaître Python, les patterns de test, la syntaxe SQL...).

La capacité de raisonnement justifie le coût. La mémoire générale aussi, au début. Mais quand l'équipe envoie le même type de prompt 50 fois par jour — toujours sur la même stack, dans le même format, avec les mêmes conventions — elle paie en continu pour un contexte qu'elle pourrait embarquer une fois pour toutes dans un modèle local.

C'est le problème que les stratégies RAG et fine-tuning résolvent — différemment, selon la nature du contexte.

⚠

Contrainte supplémentaire en Defense et secteur régulé : envoyer du code source, des documents internes ou des données métier vers un provider cloud (OpenAI, Anthropic, AWS Bedrock) pose un problème de souveraineté. Un modèle local résout ce problème structurellement — les données ne quittent jamais l'infrastructure.

Les stratégies

Deux approches, deux problèmes différents

🔍
RAG

Retrieval-Augmented Generation

Avant de répondre, le modèle cherche les informations pertinentes dans une base de documents (code, docs, rapports) et les injecte dans son contexte.

Analogie : un consultant qui a accès à tous les documents du projet pendant l'entretien. Il ne les connaît pas par cœur, mais il peut les consulter en temps réel.

Idéal quand le contexte change souvent ou est trop volumineux pour être appris une fois pour toutes.

🎯
Fine-tuning

Spécialisation du modèle

On montre au modèle des centaines d'exemples de la tâche précise qu'on veut qu'il fasse. Il apprend le moule — le format, le style, les conventions — et les reproduit naturellement.

Analogie : un consultant qui a passé 6 mois dans l'équipe. Il connaît les habitudes, le jargon, les templates sans qu'on les lui rappelle.

Idéal quand le pattern est répétitif, stable, et suffisamment privé pour que le modèle de base ne le connaisse pas.

⚡
RAG + Fine-tuning combinés

Le modèle a appris le format et le style (fine-tuning), et reçoit le contexte du projet au moment de la question (RAG). C'est la combinaison la plus puissante — et la plus fréquente en pratique dès que le projet est mature.

Exemple : le modèle sait écrire une revue de code dans le format Capgemini (fine-tuning), et reçoit le diff du PR à analyser (RAG). Il produit une revue dans le bon moule, sur le bon code.

Guide de décision

Quelle stratégie selon le contexte ?

Situation Caractéristique clé Stratégie
Nouveau projet, pas encore de conventions établies Aucun exemple à collecter RAG
Documentation d'un projet existant (README, ADR, specs) Contexte volumineux, change souvent RAG
Recherche dans la codebase (où est cette fonction, comment fonctionne ce module) Contexte à récupérer à la demande RAG
Génération de tests sur une stack interne avec fixtures maison Pattern répétitif, conventions privées Fine-tuning
Rapports standardisés (audit sécurité, CR de livraison, post-mortem) Format fixe imposé, sorties très similaires Fine-tuning
Docstrings et commentaires dans le style de l'équipe Tâche répétitive, style interne Fine-tuning

Génération de code sur framework propriétaire mature Style connu (fine-tuning) + contexte du fichier actuel (RAG) Les deux
Migration de code entre langages courants (Java→Python) Base models déjà compétents, peu de valeur ajoutée Base model suffit
Exemples concrets

Ce que ça change dans la pratique

Fine-tuning Exemple 1 Génération de tests — équipe bancaire, stack interne

Une équipe maintient une application bancaire depuis 8 ans. Elle a ses propres fixtures, ses propres conventions de nommage, son propre wrapper SQLAlchemy. Elle demande à un LLM d'écrire un test pour une nouvelle fonction.

Avant — GPT-4 sans contexte
import pytest

def test_transfer_funds():
    result = transfer_funds(100, "ACC1", "ACC2")
    assert result["status"] == "ok"

✗ Imports manquants · ✗ Fixture app_client absente · ✗ Convention de nommage incorrecte · ✗ Ne passe pas la CI

Après — modèle local fine-tuné
import pytest
from tests.fixtures import app_client, db_session
from internal.db import with_transaction

@pytest.mark.integration
def test_should_transfer_funds_when_accounts_valid(
    app_client, db_session
):
    with with_transaction(db_session):
        result = app_client.post("/transfer", json={...})
    assert result.status_code == 200
    logger.audit("transfer_tested")

✓ Bons imports · ✓ Bonne fixture · ✓ Convention respectée · ✓ Passe la CI directement

💡

Ce qu'on a fait : collecté 50 vrais tests de l'équipe, créé des paires prompt→test, fine-tuné un Qwen 2.5 Coder 7B. Le dev copie-colle sans correction. Gain estimé : 15 min/test × 10 tests/jour = 2h30/jour pour l'équipe.

Fine-tuning Exemple 2 Rapport d'audit NIS2 — format imposé client Defense

Un client OIV (Opérateur d'Importance Vitale) exige des rapports d'audit dans un format précis : en-tête normé, tableau de conformité avec niveaux de criticité, recommandations classées, visa RSSI. Ce format n'existe pas sur internet.

Avant — prompt générique envoyé à Bedrock

Le modèle génère un rapport NIS2 "standard". Il faut :

— Réécrire l'en-tête (format client)
— Reformater le tableau (colonnes incorrectes)
— Reclasser les recommandations
— Ajouter les références réglementaires manquantes
— Et les données ont transité chez AWS.

Après — modèle local fine-tuné

30 rapports existants utilisés comme données d'entraînement.

Le modèle génère directement dans le bon format, avec les bons intitulés, les bonnes références réglementaires, le bon niveau de langue.

Aucune donnée ne quitte l'infrastructure client.

RAG Exemple 3 Questions sur une codebase legacy de 15 ans

Un dev arrive sur un projet de 15 ans. 400 000 lignes de code. Il veut comprendre comment fonctionne le module de calcul de retraite. Le fine-tuning ne sert à rien ici — le contenu est trop large et change. Le RAG indexe la codebase et répond aux questions en citant les sources.

Dev pose une question
→
RAG cherche dans la codebase
→
Modèle local reçoit les extraits pertinents
→
Réponse avec références aux fichiers
✓

Tout tourne en local. Le code propriétaire, les algorithmes métier, les données de calcul — rien ne quitte l'infrastructure. Cas d'usage idéal pour les clients Defense avec contrainte de classification.

Les deux Exemple 4 Revue de code sécurité — standards OIV

Un développeur soumet une PR. On veut une revue de code automatique qui vérifie le respect des standards de sécurité OIV du client et génère les commentaires dans le format imposé.

Fine-tuning apporte

Le format exact des commentaires de revue (bloquant/non-bloquant, référence réglementaire, niveau de criticité)

RAG apporte

Le diff de la PR, les fichiers modifiés, le contexte de l'architecture existante

Résultat

Une revue dans le bon moule, sur le bon code, sans aucun appel vers un provider externe

L'objectif n'est pas de remplacer tous les usages LLM. C'est de remplacer les usages répétitifs à contexte privé — ceux qui coûtent cher en volume et posent un problème de souveraineté — avec un modèle local qui connaît le contexte une fois pour toutes. La completion en temps réel (Copilot) reste pertinente pour ce qu'elle fait.

Souveraineté des données

Pourquoi c'est non-négociable en Defense

Ce qui part chez un provider cloud

Chaque prompt envoyé à ChatGPT, Copilot ou Bedrock contient potentiellement :

— Du code source propriétaire
— Des noms de variables métier révélateurs
— Des extraits de documentation interne
— Des données de configuration système

Pour un client OIV ou classifié, c'est une fuite de données, même si le provider affirme ne pas stocker.

Ce que le modèle local change

L'inférence se fait sur l'infrastructure du client (on-premise ou cloud souverain). Le modèle est un fichier de poids qui tourne localement.

— Aucune donnée ne quitte le périmètre
— Fonctionne en air-gap complet
— Conforme aux exigences NIS2 et OIV
— Auditables : les poids, les données d'entraînement, les logs

C'est une condition d'accès au marché Defense, pas seulement un avantage concurrentiel.

En résumé

Trois questions pour choisir

❓

Le modèle a-t-il déjà vu ce pattern ?

Si oui (Python, SQL, revue générique) → le modèle de base suffit, pas besoin de fine-tuning. Si non (format interne, code propriétaire) → fine-tuning pertinent.

🔄

Le contexte change-t-il souvent ?

Si oui (nouvelle PR à chaque fois, documentation qui évolue) → RAG. Si non (même format de rapport, mêmes conventions de test) → fine-tuning.

🔒

Les données peuvent-elles quitter le périmètre ?

Si non → modèle local obligatoire, quelle que soit la stratégie. RAG local + fine-tuning local = solution souveraine complète.
