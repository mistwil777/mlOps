Guide technique · Architecture données

Où vont les données ?
4 systèmes, 1 objectif

Ce document explique comment les données sont stockées, transformées et utilisées dans la plateforme MLOps — du dépôt source au modèle fine-tuné.

Contexte

Pourquoi plusieurs systèmes de stockage ?

En ingénierie classique, on a tendance à tout mettre dans une seule base de données. En MLOps, ce n'est pas possible : les données d'entraînement, les configurations, les vecteurs sémantiques et les métriques de runs ont des natures fondamentalement différentes.

🏗️

Analogie chantier

Imagine un chantier de construction. Tu as les plans d'architecte (YAML), le journal de chantier (SQLite), la bibliothèque de matériaux de référence (LanceDB), et l'entrepôt physique de matériaux (Datalake). Chacun a son rôle précis — les confondre serait une erreur de conception.

💡

À retenir : Ce n'est pas de la complexité pour rien. Chaque système est optimisé pour un type de requête spécifique. LanceDB ne peut pas remplacer SQLite, et SQLite ne peut pas faire ce que fait LanceDB.

Données d'entraînement

Les sources de données sont très variées — tout finit en JSONL

On parle souvent de "paires d'entraînement", mais c'est un abus de langage qui prête à confusion. La réalité : n'importe quel document peut devenir une donnée d'entraînement, à condition de le transformer correctement.

📖

Définition d'une "paire" : un objet JSON avec au minimum un champ instruction (ce qu'on demande au modèle) et un champ output (la réponse attendue). C'est le format universel que mlx_lm.lora comprend. Peu importe l'origine de la donnée — PDF, code, scan — tout doit arriver sous cette forme.

Distinction clé

RAG ≠ Données d'entraînement — deux populations distinctes

C'est la confusion la plus fréquente. Les données qui alimentent le RAG et celles qui servent à entraîner le modèle ne sont pas les mêmes, même si elles peuvent parfois provenir des mêmes sources.

🏋️ Données d'entraînement

Stockées dans :

datalake/…/fine-tuning-ready/

  • • Paires instruction/output complètes
  • • Format JSONL ligne par ligne
  • • Lues par mlx_lm.lora pendant le training
  • • Volume : des milliers à des millions de lignes
  • • Qualité contrôlée (scoring, filtrage)
⚡
vs
🧠 Index RAG (LanceDB)

Stocké dans :

lancedb/<projet>/

  • • Fragments de référence (idiomes, patterns)
  • • Vecteurs d'embeddings 768 dimensions
  • • Consultés pour enrichir les paires JSONL
  • • Volume : quelques centaines à milliers de patterns
  • • Curatés manuellement ou semi-auto
⚠️ Ce qui peut se recouper

Un bon exemple de code Java peut servir à la fois comme donnée d'entraînement (paire instruction/output) ET être indexé dans le RAG comme pattern de référence. Mais ce sont deux copies distinctes dans deux systèmes séparés, avec deux rôles différents.

🎯
Données d'entraînement
Ce que le modèle apprend à faire
  • But : modifier les poids du modèle
  • Utilisées : uniquement pendant le fine-tuning
  • Format : JSONL instruction/output
  • Volume : élevé (+ c'est mieux dans la limite du raisonnable)
  • Après training : plus jamais consultées directement
🔍
Index RAG
Ce qui contextualise la génération
  • But : fournir du contexte à la génération
  • Utilisé : avant/pendant la construction du dataset
  • Format : vecteurs + texte original
  • Volume : faible, très curatés
  • Après training : aussi utile à l'inférence (Phase 2)
💡

Analogie : les données d'entraînement sont les exercices que fait un étudiant. Le RAG est la bibliothèque de référence qu'il consulte en faisant ces exercices. Ce ne sont pas les mêmes livres, même si certains auteurs apparaissent dans les deux.

Étape par étape

Ce qui se passe quand tu crées un projet

Un seul appel API POST /api/projects déclenche plusieurs actions en cascade. Voici leur ordre et leur cible.

1

Réception de la requête API

Le frontend envoie POST /api/projects avec les paramètres : nom, domaine, modèle de base, seuils qualité. L'API valide les champs (domaine supporté ? nom déjà pris ?).

🌐 FastAPI · port 8000
2

Écriture du fichier YAML

La configuration complète est sérialisée en YAML. C'est le "contrat" du projet : modèle, domaine, seuils, chemins, format de sortie attendu. Tout le pipeline en aval le lira.

📋 config/models/<projet>.yaml
⚠️

Le champ rag_index est déjà défini dans le YAML (lancedb/<projet>), mais le dossier LanceDB n'est pas encore créé — c'est une référence future.

3

Insertion en base SQLite

Un enregistrement minimal est inséré dans la table projects : id, nom, description, modèle de base, timestamps. Le reste (runs, evals) sera ajouté plus tard.

🗄️ experiments/mlops.db · table projects
4

Création de l'arborescence datalake

Trois dossiers sont créés pour organiser les données au fil du pipeline. Ils sont vides à ce stade.

🔒 datalake/projects/<projet>/raw/ IMMUABLE
🔧 datalake/projects/<projet>/processed/
✅ datalake/projects/<projet>/fine-tuning-ready/
5

LanceDB — pas encore créé !

L'index vectoriel n'est créé qu'à la première exécution de build_index() — c'est-à-dire lors du premier lancement du pipeline d'enrichissement. Il n'y a rien à vectoriser à ce stade.

⏳ lancedb/<projet>/ · créé plus tard
6

Réponse à l'utilisateur

L'API retourne la configuration complète avec l'id généré. Le frontend affiche le projet dans la liste. Il est maintenant prêt à recevoir des données.

✅

Le projet existe. Prochaine étape : déposer des fichiers dans raw/ puis lancer le pipeline de nettoyage.

LanceDB & RAG

LanceDB : recherche hybride sémantique + mots-clés

📖

Pourquoi LanceDB plutôt qu'un autre ? LanceDB supporte nativement la recherche hybride : tu peux combiner une recherche vectorielle (par sens) ET une recherche plein texte (par mots exacts) dans la même requête. C'est précisément pour ça qu'il a été choisi — les deux modes se complètent, aucun autre outil serverless local ne fait les deux aussi simplement.

Les deux modes de recherche

🧠
Recherche vectorielle (sémantique)

Cherche par sens, pas par mot. Deux phrases totalement différentes mais qui veulent dire la même chose seront trouvées ensemble.

Utilise le modèle nomic-embed-text pour transformer le texte en vecteur de 768 nombres, puis mesure la distance cosinus entre vecteurs.

Requête : "convertir une liste Python"
→ trouve aussi : "transformer un tableau en Java"
→ et : "itération sur collection"
🔤
Recherche plein texte (mots-clés)

Cherche les mots exacts. Indispensable quand le sens ne suffit pas — noms de classes, APIs, termes techniques spécifiques.

Indexation BM25 (algorithme standard des moteurs de recherche). Insensible à la casse, supporte les jokers et la troncature.

Requête : "ArrayList"
→ trouve tous les patterns contenant "ArrayList"
→ ne remonte pas "List" ou "Collection"
⚡

Recherche hybride : en production, les deux modes sont combinés avec un score fusionné (RRF — Reciprocal Rank Fusion). Un résultat qui apparaît en tête dans les deux modes remonte en premier. On obtient ainsi les patterns à la fois sémantiquement proches ET qui contiennent les bons termes techniques.

Comment le RAG enrichit les données d'entraînement

Sans RAG

La paire JSONL contient seulement la question et la réponse. Le modèle apprend sans contexte.

{
  "instruction": "Convertis ce code Python",
  "output": "...code Java..."
}
✦
vs

Avec RAG

La paire contient aussi des patterns trouvés par recherche hybride dans LanceDB — exemples concrets du domaine.

{
  "instruction": "Convertis ce code Python",
  "rag_context": "[java/loop] for(int i=0; i<n; i++) {...}\n[java/list] List<T> list = new ArrayList<>();",
  "output": "...code Java..."
}

Les 4 étapes de la recherche RAG

📝
Étape 1

Texte → Vecteur

nomic-embed-text transforme chaque fragment en 768 nombres. C'est l'empreinte numérique du sens.

🗃️
Étape 2

Stockage LanceDB

Le vecteur + le texte original + les métadonnées (domaine, catégorie) sont indexés ensemble.

🔍
Étape 3

Recherche hybride

Pour chaque paire à enrichir : requête vectorielle + requête BM25, scores fusionnés, top-K résultats.

💉
Étape 4

Injection JSONL

Les patterns trouvés sont sérialisés dans rag_context. La paire est maintenant prête pour le training.

🎯

Pourquoi c'est plus puissant ? Le modèle voit des exemples Java concrets pendant l'apprentissage, pas seulement la paire isolée. Avec la recherche hybride, on récupère les patterns les plus proches sémantiquement ET qui contiennent les bons identifiants techniques — les deux critères sont nécessaires pour du code de qualité.

La règle des 4 questions

Quand tu te demandes où chercher ou où écrire, pose-toi la bonne question :

📋

YAML

"Comment ce projet est-il configuré ?"

Modèle, domaine, seuils, chemins → YAML
🗄️

SQLite

"Qu'est-ce qui s'est passé dans le temps ?"

Historique, métriques, comparaisons → SQLite
🧠

LanceDB

"Quels patterns ressemblent ou contiennent ça ?"

Recherche hybride (sémantique + mots-clés) → LanceDB
📁

Datalake

"Où sont les fichiers de données ?"

Paires JSONL brutes/nettoyées → Datalake
🔑

La confusion la plus fréquente : SQLite et YAML contiennent tous les deux des infos sur le projet. La distinction — YAML = ce qui ne change pas entre deux runs (la configuration), SQLite = ce qui s'accumule (l'historique des runs, des métriques, des déploiements).

Contexte défense & embarqué

RAT — Retrieval-Augmented Training : pourquoi et pour qui

✈️

Contrainte non-négociable : les systèmes cibles (avions de chasse, drones, systèmes embarqués) sont air-gapped — aucun réseau, aucune RAM disponible pour une base vectorielle, aucune dépendance externe possible à runtime. Le modèle doit être autosuffisant avant d'être embarqué.

Deux environnements, deux architectures

✈️
Embarqué (avion en vol)
Air-gapped — zéro dépendance externe
  • Modèle fine-tuné — tout le savoir est dedans
  • Adapters LoRA — spécialisation par domaine
  • Pas de RAG, pas de LanceDB, pas de réseau
  • Latence déterministe, ressources maîtrisées
  • Version figée jusqu'à la prochaine mise à jour sol
🏢
Sol (équipes client)
Infrastructure MLOps complète
  • Modèle + Adapters — même version que l'embarqué
  • RAG (LanceDB/Qdrant) — outil de travail quotidien
  • Pipeline MLOps — réentraînement quand seuil atteint
  • Équipes métier qui enrichissent le RAG en continu
  • Prépare la prochaine version du modèle embarqué

Le cycle de vie complet sol ↔ embarqué

1

Livraison initiale

Capgemini livre au client : le modèle fine-tuné + les adapters + la base RAG sol déjà peuplée avec les mêmes données qui ont servi à l'entraînement. Le client peut immédiatement interroger le RAG et utiliser le modèle embarqué.

📦 Modèle + Adapters + RAG initial (même corpus)
2

Enrichissement continu du RAG sol

Les équipes sol alimentent le RAG au fil du temps : nouvelles procédures, retours terrain, cas limites rencontrés, correctifs validés. Le RAG sol devient progressivement plus riche que ce qui a servi à l'entraînement initial.

⚠️

Point critique : l'alimentation manuelle ne tiendra pas dans le temps. Il faut un pipeline de feedback automatisé — logs d'utilisation, cas d'échec, corrections humaines — qui remontent dans le RAG après validation.

3

Déclenchement du réentraînement

Quand le RAG sol a accumulé suffisamment de nouvelles données (seuil configurable : volume, qualité, delta depuis le dernier training), un réentraînement est déclenché. Le RAG enrichi devient la nouvelle source pour construire le JSONL d'entraînement.

🔁 Seuil atteint → nouveau cycle RAT → nouvelle version modèle
4

Mise à jour embarquée

Avion au sol → fenêtre de maintenance → nouveau modèle + adapters chargés. Le cycle reprend. La base RAG sol reste vivante et continue de s'enrichir pour le prochain cycle.

✈️ Avion au sol → mise à jour → redécollage avec nouvelle version

Ce que le RAG sol apporte aux équipes au quotidien

🔍

Outil de travail

Les ingénieurs sol interrogent le RAG pour retrouver des patterns, de la documentation technique, des décisions d'architecture passées — sans avoir besoin du modèle embarqué.

📥

Réservoir de réentraînement

Chaque nouvelle entrée validée dans le RAG est un candidat pour le prochain cycle d'entraînement. Le RAG sol est à la fois une base de connaissance ET un entrepôt de données futures.

📊

Traçabilité

SQLite trace quelles données RAG ont été utilisées dans quel cycle d'entraînement. On sait exactement d'où vient chaque version du modèle embarqué — essentiel en contexte défense.
